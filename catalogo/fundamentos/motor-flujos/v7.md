# Fundamentos: motor de flujos

## Versión

7

Con estas 9 piezas se construye cualquier operativa. Todo lo demás es una combinación de ellas.

| # | Pieza | Qué es | Dónde vive |
|---|---|---|---|
| 1 | Ancla | Un campo de dato con nombre fijo (`_negocio.telefono_`) | catálogo de anclas |
| 2 | Skill | Una tarea con entradas y salidas en anclas | `skills` |
| 3 | Ejecutor | Quién hace la skill: modelo, herramienta, integración o humano | `ejecutores` |
| 4 | Pipeline | Una consulta de MongoDB (Aggregation Pipeline) | dentro de 5 y 6 |
| 5 | Flujo | Pasos conectados: nodos y aristas | `flujos` |
| 6 | Disparador | Cuándo arranca un flujo | `disparadores` |
| 7 | Evento | Algo que pasó y se evaluó | `eventos` |
| 8 | Corrida | Una ejecución de un flujo | `corridas` |
| 9 | Redactor | Convierte una intención (texto) en una definición (JSON) | módulo del panel + `POST /v1/redactor` |

---

## 1. Ancla
El nombre único de un dato. Todas las demás piezas leen y escriben anclas, nunca campos sueltos.
```json
{ "id": "_reserva.estado_", "tipo": "texto", "valores": ["pendiente", "confirmada", "cancelada"] }
```

## 2. Skill
Qué se hace, no quién lo hace.
```json
{ "id": "enviar-whatsapp", "entradas": ["_cliente.telefono_", "_mensaje.texto_"],
  "salidas": ["_mensaje.enviado_"], "ejecutorId": "whatsapp-n8n", "systemPromptId": null }
```

## 3. Ejecutor
Cómo se hace la skill. Tipos: `modelo`, `herramienta`, `integracion`, `humano`, `agente_externo`.
Catálogo D1 `ejecutores` + `skill.ejecutorId` (null = implícito `agente_externo`).
```json
{ "id": "whatsapp-n8n", "tipo": "integracion",
  "config": { "url": "https://n8n…/webhook/wa", "metodo": "POST", "asincrono": true },
  "timeout_s": 30, "reintentos": 2, "espera_reintento_s": 10, "activo": true, "version": 1 }
```

## 4. Pipeline
Lista de etapas de MongoDB. Solo lee, no escribe.
- Etapas permitidas: `$match`, `$lookup`, `$project`, `$group`, `$sort`, `$limit`, `$unwind`, `$addFields`.
- Etapas prohibidas: `$out` y `$merge`, porque escriben en la base de datos.
- Si devuelve documentos, la respuesta es sí y cada documento es una salida. Si no devuelve ninguno, la respuesta es no.
```json
[ { "$match": { "_reserva.estado_": "pendiente" } }, { "$project": { "reserva": "$_id" } } ]
```

## 5. Flujo
Un grafo de nodos y aristas. Tipos de nodo: `inicio`, `skill`, `decision` (que lleva una condición), `subflujo` y `fin`.
```json
{ "id": "recordatorio", "version": 1,
  "nodos": [ {"id":"inicio","tipo":"inicio"}, {"id":"enviar","tipo":"skill","skill":"enviar-whatsapp"}, {"id":"fin","tipo":"fin"} ],
  "aristas": [ {"desde":"inicio","hacia":"enviar"}, {"desde":"enviar","hacia":"fin"} ] }
```

## 6. Disparador
Cuándo arranca un flujo. Varios disparadores de un mismo flujo funcionan como «o»: arranca con cualquiera de ellos.

| tipo | Qué lo despierta | Sobre qué corre el pipeline |
|---|---|---|
| `manual` | el botón «Lanzar» | no tiene pipeline |
| `horario` | el cron global de cada minuto, si coincide su `cron` | una colección entera |
| `cambio_datos` | una escritura en la API | el evento del cambio |
| `webhook` | `POST /v1/disparar/:flujo/:token` | el evento recibido |

```json
{ "id": "d-07", "flujo_id": "recordatorio", "tipo": "horario", "activo": true,
  "cron": "0 * * * *", "coleccion": "reservas",
  "pipeline": [ { "$match": { "_reserva.estado_": "pendiente" } } ],
  "anti_bucle": true, "agrupar_segundos": 0 }
```
Campos según el tipo:
- `horario`: `cron`, `coleccion`.
- `cambio_datos`: `coleccion`, `operaciones` (`crear`|`actualizar`|`borrar`).
- `webhook`: `token` (lo genera la API).

## 7. Evento
Cada cambio de datos y cada webhook se guarda primero en `eventos`. Después se ejecuta sobre él el pipeline de cada disparador que aplique, con una etapa inicial que fija ese evento: `{$match:{_id}}`.
```json
{ "_id": "ev-8f21", "tipo": "cambio_datos", "coleccion": "reservas", "documento_id": "r-552",
  "operacion": "actualizar", "antes": {…}, "despues": {…}, "body": null, "origen": "panel",
  "creado": "…", "resultado": [ { "disparador_id": "d-12", "lanzo": true, "corrida_id": "c-91aa" } ] }
```
- Los eventos se borran a los 30 días, con un índice TTL sobre `creado`.
- Anti-bucle: un evento cuyo `origen` es una corrida del mismo flujo no lo vuelve a disparar.

## 8. Corrida
Una ejecución concreta de un flujo, con su versión fijada.
```json
{ "id": "c-91aa", "flujo_id": "recordatorio", "version": 1, "estado": "en_curso",
  "disparador_id": "d-07", "evento_id": null, "datos": {…}, "pasos": [ … ], "errores": [] }
```

## 9. Redactor: intención → definición
- **Intención:** lo que escribes en texto.
- **Definición:** el JSON que se guarda (de un disparador, un flujo o un pipeline).
- **Redactor:** el módulo que traduce la intención en definición. Hay uno solo para todas las definiciones, con el texto a la izquierda y el JSON a la derecha.

El recorrido es siempre el mismo:

1. Escribes el texto.
2. La skill `generar-definicion` (ejecutor `modelo`, vía `POST /v1/redactor`) produce el JSON. Recibe el esquema y el contexto: tus anclas, skills y flujos reales. Sin `OPENAI_API_KEY` responde un mock heurístico + validación.
3. **Validar:** comprueba el esquema, que los campos y skills existen y que solo se usan etapas permitidas.
4. **Probar:** el pipeline se ejecuta contra eventos o datos reales y te dice qué habría lanzado (dry-run; no crea corridas).
5. **Confirmar:** guardas tú, y cada guardado crea una versión nueva.

Cada uso del Redactor se registra en D1 `skill_ejecuciones` como ejecución de `generar-definicion`.

La IA solo actúa al **crear**. Al **ejecutar**, se usará la definición guardada a través de la skill `consultar-datos` (ejecutor `herramienta`), que es rápida, sin coste y determinista (aún pendiente).

## Límites
- Un pipeline solo lee. Cualquier acción la hace una skill.
- Para que algo **no** haya pasado (por ejemplo, «sin confirmar en 2 horas») se usa `horario` con pipeline, no `cambio_datos`.
- Una condición «y» entre disparadores se pone como una caja `decision` justo después de `inicio`.
