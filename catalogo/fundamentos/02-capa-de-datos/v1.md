## Mapa de la Capa de Datos (Objetos 1 al 5)

La **Capa de Datos** define dónde se guarda físicamente la información en MongoDB Atlas y cómo se traduce a **Campos ancla** (`_ruta.campo_`) para que las Skills y los Flujos trabajen sin acoplarse a los nombres internos de las tablas:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. CLUSTER (D1: clusters + mongo_config_cluster)                            │
│    Servidor MongoDB Atlas · Guarda la URI cifrada con AES-GCM               │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 1 Cluster aloja 1..N Bases de datos
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. BASE DE DATOS / PROYECTO (D1: proyectos + esquema_empujes)               │
│    Ej.: "reservas" (BD: software_reservas) | "llamadas" (software_llamadas) │
│    Incluye: colecciones[], relaciones[] (ER), Operativa (huecos) y Empujes  │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 1 Proyecto contiene 1..N Colecciones
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. COLECCIÓN (D1: proyectos.colecciones · Mongo: colección física)          │
│    Modo de escritura: "unico_por_negocio" (1:1) vs. "multiple" (1:N)        │
│    Incluye: Explorador de Documentos en vivo en la pestaña "Datos"          │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 1 Colección tiene 1..N Campos MongoDB
                                       ▼
┌────────────────────────────────────┐   ┌────────────────────────────────────┐
│ 4. CAMPO MONGODB (D1: campos_mongo)│◄─►│ 5. CAMPO ANCLA (D1: anclas)        │
│    Propiedad física + tipo BSON    │1:1│    Contrato lógico `_ruta.campo_`  │
│    Genera el validador $jsonSchema │   │    + aliases[] + sensible          │
└────────────────────────────────────┘   └────────────────────────────────────┘
```

## Objeto 1 · Cluster (`clusters`)

### 1. Qué es (en 1 frase)
Es el servidor de **MongoDB Atlas** donde se alojan una o varias bases de datos del sistema, y el único lugar donde se guarda (cifrada) la cadena de conexión (`mongodb+srv://...`).

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `clusters`: metadatos del cluster y estado del último empuje de esquema (`last_sync_*`).
  - Tabla `mongo_config_cluster`: guarda la URI cifrada con AES-GCM (`ciphertext`, `iv`, `uri_hint`, `db_name`).
- **En MongoDB Atlas:** Representa el cluster físico de Atlas al que se conecta el Worker.
- **En la API (`/v1/clusters`):**
  - `GET /v1/clusters` y `GET /v1/clusters/:id` *(públicos)*: listan y leen la ficha del cluster.
  - `POST /v1/clusters` y `PUT /v1/clusters/:id` *(requieren `Bearer inv_...`)*: crean o actualizan el cluster (incluyendo `autoSync`).
  - `DELETE /v1/clusters/:id` *(requiere `Bearer inv_...`)*: borra el cluster si no tiene bases de datos asociadas.
  - `GET /v1/clusters/:id/mongo-config` *(público)*: devuelve si la URI está configurada y una pista enmascarada (`uriHint`), **nunca la URI real**.
  - `POST /v1/clusters/:id/mongo-config` y `DELETE /v1/clusters/:id/mongo-config` *(requieren `Bearer inv_...`)*: guardan o eliminan la URI cifrada.
- **En el Panel UI:** Barra lateral **Catálogo → Clusters** (`#panel-clusters`). Al hacer clic en un cluster se abre la ficha (`dlgCluster`) con **3 pestañas**:
  - **Resumen:** nombre, descripción, interruptor `autoSync` y resumen de la última sincronización.
  - **Conexión:** campo para pegar la URI de MongoDB Atlas y botones **Guardar**, **Probar** y **Borrar**.
  - **Asociados → subpestaña Bases de datos:** lista las Bases de datos (Proyectos) alojadas en ese cluster.

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `clusters.id` | `string` (`atlas-principal`) | Sí | Identificador único del cluster en formato slug. |
| `nombre` | `clusters.nombre` | `string` (máx. 120 chars) | Sí | Nombre visible en el panel (ej. «Cluster Atlas»). |
| `descripcion` | `clusters.descripcion` | `string` (máx. 280 chars) | No | Explicación de qué entorno o cuenta de Atlas representa. |
| `autoSync` | `clusters.auto_sync` | `boolean` (`0` o `1` en D1) | No | Si es `true`, cada cambio en colecciones o campos MongoDB empuja automáticamente el esquema a Atlas tras 1,5 s de espera (debounce). |
| `lastSync` | `last_sync_at`, `last_sync_ok`, `last_sync_proyecto`, `last_sync_summary` | `object \| null` | Auto | Objeto calculado con el resultado del último empuje a Atlas (`at`, `ok`, `proyecto`, `db`, `created[]`, `updated[]`, `error?`). |
| `color` | `clusters.color` | `string \| null` (`#RRGGBB`) | No | Color hexadecimal del icono en el catálogo. |
| `proyectos` | *(join con `proyectos.cluster_id`)* | `Proyecto[]` | Auto | Lista de Bases de datos alojadas en este cluster. |
| `uri` *(solo entrada en `POST .../mongo-config`)* | `mongo_config_cluster.ciphertext` + `iv` | `string` (`mongodb+srv://...`) | Sí (al conectar) | Cadena de conexión a Atlas. Se cifra antes de tocar D1 y jamás se devuelve en un `GET`. |

### 4. Conexiones (Hacia arriba y hacia abajo)
- **Hacia arriba:** Es la raíz física de la Capa de Datos; se conecta al exterior con MongoDB Atlas.
- **Hacia abajo (quién lo usa):** Lo referencian las **Bases de datos / Proyectos** mediante `proyecto.clusterId → cluster.id` (`DEFAULT_CLUSTER_ID = "atlas-principal"`).

### 5. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:** Cuando pulsas **Empujar esquema** en una Base de datos (o cuando `autoSync: true` detecta un cambio en campos/colecciones), el Worker descifra la URI del cluster en memoria y crea las colecciones y validadores `$jsonSchema` en Atlas.
- **En Tiempo de Ejecución:** Cada vez que un Disparador evalúa un pipeline, una Corrida lee entradas o escribe salidas, o se abre el Explorador de Documentos, el motor resuelve `proyecto.clusterId → mongo_config_cluster` para conectarse al servidor correcto.

### 6. Reglas y límites que no se pueden romper (Invariantes)
- **Protección contra borrado accidental (`409 Conflict`):** No se puede eliminar un cluster (`DELETE /v1/clusters/:id`) si todavía tiene alguna Base de datos (`proyectos.cluster_id`) apuntando a él.
- **Opacidad total de credenciales:** Ningún endpoint devuelve jamás la URI ni contraseñas en claro; si MongoDB lanza un error de conexión, el Worker limpia (`scrub`) cualquier rastro de `mongodb://` antes de responder.
- **Rutas antiguas deprecadas (`410 Gone`):** `POST /v1/mongo/config` y `DELETE /v1/mongo/config` devuelven `410`; la URI siempre se configura por cluster en `/v1/clusters/:id/mongo-config`.

### 7. Ejemplo real en producción
```json
{
  "id": "atlas-principal",
  "nombre": "Cluster Atlas",
  "descripcion": "Cluster por defecto (migración desde URI por Base de datos).",
  "color": "#b89a1a",
  "autoSync": false,
  "lastSync": {
    "at": "2026-10-24T10:27:53.649Z",
    "ok": true,
    "proyecto": "llamadas",
    "auto": false,
    "db": "software_llamadas",
    "updated": ["clientes", "llamadas"]
  }
}
```

## Objeto 2 · Base de datos / Proyecto (`proyectos`)

### 1. Qué es (en 1 frase)
Es la ficha de un software completo (como el `Software de reservas` o el `Software de llamadas`) que agrupa su nombre físico de base de datos en MongoDB, sus colecciones, las relaciones entre ellas, sus skills asociadas y el historial de empujes de esquema a Atlas.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `proyectos`: definición principal, `base_datos`, `cluster_id`, `colecciones` (JSON), `relaciones` (JSON).
  - Tabla `proyecto_versions`: versiones históricas del documento markdown del proyecto (`numero`, `fecha`, `markdown`, `hash`).
  - Tabla `proyecto_skills`: relación muchos-a-muchos (`N:M`) entre proyectos y skills.
  - Tabla `esquema_empujes`: historial auditable de cada vez que se empujó el esquema de este proyecto hacia MongoDB Atlas (`id`, `proyecto_id`, `ts`, `modo`, `ok`, `resumen`, `detalle_json`).
- **En MongoDB Atlas:** Corresponde a la base de datos física indicada en `baseDatos` (por ejemplo, `software_reservas` o `software_llamadas`).
- **En la API (`/v1/proyectos`, con alias compatible `/v1/esquemas`):**
  - `GET /v1/proyectos` y `GET /v1/proyectos/:id` *(públicos)*.
  - `POST /v1/proyectos`, `PUT /v1/proyectos/:id` y `DELETE /v1/proyectos/:id` *(requieren `Bearer inv_...`)*.
  - `GET /v1/proyectos/:id/diagrama?coleccion=&format=mermaid` *(público)*: genera el diagrama Entidad-Relación (ER) de sus colecciones, campos y relaciones.
  - `GET /v1/proyectos/:id/operativa` *(público)*: analiza todas las skills asociadas al proyecto, enlaza las `salidas[]` de unas con las `entradas[]` de otras y detecta **huecos** (anclas que una skill necesita de entrada pero ninguna skill del proyecto produce).
  - `POST /v1/proyectos/:id/crear-bd` *(requiere `Bearer inv_...`)*: empuja el DDL (colecciones + validadores `$jsonSchema` + índices) hacia MongoDB Atlas (admite `?dryRun=1` para simular sin tocar Atlas).
  - `GET /v1/proyectos/:id/empujes?limit=&cursor=&estado=&desde=&hasta=` *(público)*: devuelve el historial paginado de empujes de esquema.
- **En el Panel UI:** Barra lateral **Catálogo → Base de datos** (`#panel-proyectos`). Al abrir un proyecto (`dlgProyecto`) dispone de **9 pestañas principales** y un botón superior **Empujar esquema**:
  1. **Resumen:** datos de la BD, cluster y métricas.
  2. **Asociados** *(con 4 subpestañas)*: **Cluster**, **Colecciones**, **Campos** y **Skills**.
  3. **Operativa** *(con 3 subpestañas)*: **Mapa** (grafo de cómo las salidas de una skill alimentan las entradas de otra), **Huecos** (alertas rojas `⛔` de anclas de entrada sin productor) y **Atajos**.
  4. **Flujos:** lista los flujos de este proyecto y botón `+ Flujo`.
  5. **Documento:** notas de diseño versionadas en markdown.
  6. **Diagrama:** diagrama Entidad-Relación (ER) interactivo de las colecciones y relaciones.
  7. **Empujar:** panel para lanzar `crear-bd` en modo real o simulación (`dry-run`).
  8. **Historial:** registro cronológico de `esquema_empujes` con filtros por estado y fechas.
  9. **Interno:** `id`, `baseDatos`, versión y hash.

### 3. Tabla de campos (incluyendo `relaciones[]` y `esquema_empujes`)
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `proyectos.id` | `string` (`reservas`, `llamadas`) | Sí | Identificador corto del proyecto. |
| `nombre` | `proyectos.nombre` | `string` | Sí | Nombre comercial del software (ej. «Software de llamadas»). |
| `baseDatos` | `proyectos.base_datos` | `string` (`software_llamadas`) | Sí | Nombre exacto de la base de datos física dentro de MongoDB Atlas. |
| `clusterId` | `proyectos.cluster_id` | `string` (`atlas-principal`) | Sí | ID del Cluster donde reside esta base de datos. |
| `colecciones` | `proyectos.colecciones` | `Array<{ id, descripcion, color?, modo_escritura? }>` | No | Lista de colecciones de esta BD. Aquí se define su `modo_escritura` (`"unico_por_negocio"` o `"multiple"`). |
| `relaciones` | `proyectos.relaciones` | `Array<{ desde, hacia, tipo }>` | No | **Relaciones entre colecciones** del tipo `"coleccionA.campo" → "coleccionB._id"`, con cardinalidad `"N:1"`, `"1:1"`, `"1:N"` o `"N:M"`. |
| `skills` | *(tabla `proyecto_skills`)* | `string[]` | No | IDs de las skills vinculadas a este proyecto (usadas para calcular la pestaña **Operativa**). |
| `agentes` | `proyectos.agentes_json` | `string[]` | No | Lista informativa de agentes vinculados al proyecto. |
| `versiones` | *(tabla `proyecto_versions`)* | `Array<{ numero, fecha, markdown, hash }>` | Auto | Historial de versiones del documento descriptivo del proyecto. |
| `color` | `proyectos.color` | `string \| null` (`#RRGGBB`) | No | Color hexadecimal del proyecto en el panel. |

#### Sub-objeto incluido en Proyecto: Registro de Empuje (`esquema_empujes`)
Cada vez que se ejecuta `POST /v1/proyectos/:id/crear-bd` (o el `autoSync` del cluster), se guarda una fila en `esquema_empujes` con:
- `id` (`emp-...` o UUID), `proyectoId`, `ts` (fecha ISO), `modo` (`"real"` | `"dry-run"` | `"auto"`), `ok` (`true` | `false`), `resumen` (ej. `"Actualizadas: clientes, llamadas"`) y `detalle` (plan de colecciones creadas/actualizadas o error devuelto por Atlas).

### 4. Conexiones (Hacia arriba y hacia abajo)
- **Hacia arriba:** Pertenece a un **Cluster** (`proyecto.clusterId → cluster.id`).
- **Hacia abajo:**
  - Contiene las **Colecciones** (`proyectos.colecciones`) y sus **Relaciones** (`proyectos.relaciones`).
  - Agrupa los **Campos MongoDB** (`campos_mongo.proyecto` y `base_datos`) y los **Campos ancla** (`anclas.base_datos`).
  - Contiene los **Flujos** (`flujos.proyecto_id`, con borrado en cascada `ON DELETE CASCADE`) y da contexto a las **Corridas**, **Eventos** y **Ejecuciones** en MongoDB.

### 5. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:**
  - Valida que todas las `relaciones[]` apunten a colecciones que existan dentro de `colecciones[]`.
  - Genera el diagrama ER (`GET /v1/proyectos/:id/diagrama`) y el mapa de encadenamiento de skills (`GET /v1/proyectos/:id/operativa`).
  - Empuja el esquema `$jsonSchema` a MongoDB Atlas (`POST /v1/proyectos/:id/crear-bd`).
- **En Tiempo de Ejecución:** Determina en qué base de datos física de MongoDB Atlas se guardan y consultan las corridas (`corridas`), los eventos (`eventos`), las ejecuciones (`ejecuciones`) y los documentos de negocio de ese software.

### 6. Reglas y límites que no se pueden romper (Invariantes)
- **Integridad de relaciones (`400 Bad Request`):** Si añades una relación `{ "desde": "facturas.cliente_id", "hacia": "clientes._id" }` y `facturas` o `clientes` no están dadas de alta en `proyecto.colecciones`, la API rechaza el guardado con error `400` (`"relación.desde referencia colección inexistente"`).
- **Actualización sin crear versión innecesaria:** Si haces `PUT /v1/proyectos/:id` enviando solo `{ colecciones, relaciones }` o `{ skills }` o `{ color }` sin cambiar el markdown, la API actualiza la estructura sin inflar el número de versión en `proyecto_versions`.

### 7. Ejemplo real en producción (`llamadas`)
```json
{
  "id": "llamadas",
  "nombre": "Software de llamadas",
  "descripcion": "Software de llamadas: clientes y registro de llamadas. Relación llamadas.cliente_id → clientes._id (N:1).",
  "color": "#5a9a3a",
  "baseDatos": "software_llamadas",
  "clusterId": "atlas-principal",
  "colecciones": [
    { "id": "clientes", "descripcion": "", "color": "#b89a1a" },
    { "id": "llamadas", "descripcion": "", "color": "#8a6a2a" }
  ],
  "relaciones": [
    { "desde": "llamadas.cliente_id", "hacia": "clientes._id", "tipo": "N:1" }
  ],
  "skills": ["e2e-escribir-llamada", "procesar-llamada-n8n", "consultar-datos"]
}
```

## Objeto 3 · Colección (`colecciones`)

### 1. Qué es (en 1 frase)
Es una tabla de documentos dentro de la base de datos de MongoDB de un proyecto (como `negocios`, `procesos`, `clientes` o `llamadas`), que define además si cada negocio tiene **un único documento fijo (1:1)** o **múltiples documentos históricos (1:N)**.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:** No tiene una tabla SQL separada; vive como un array de objetos JSON dentro de la columna `proyectos.colecciones`.
- **En MongoDB Atlas:** Es la colección física dentro de la base de datos del proyecto (`db.collection(id)`).
- **En la API:**
  - `GET /v1/colecciones?proyecto=<id>` *(público)*: devuelve el catálogo aplanado de todas las colecciones con el recuento de campos (`nCampos`).
  - **Cómo se crea, edita o borra:** mediante `PUT /v1/proyectos/:id` enviando el array `{ "colecciones": [ ... ] }`. No existen `POST /v1/colecciones` ni `DELETE /v1/colecciones`.
  - **Explorador de Documentos en vivo:**
    - `GET /v1/proyectos/:id/colecciones/:col/documentos?limit=50&after=&filter=&sort=&fields=&negocio=&incluirSensible=` *(requiere `Bearer inv_...`)*.
    - `GET /v1/proyectos/:id/colecciones/:col/documentos/:docId?incluirSensible=` *(requiere `Bearer inv_...`)*.
- **En el Panel UI:** Barra lateral **Catálogo → Colecciones** (`#panel-colecciones`). Al abrir una colección (`dlgColeccion`) tiene **4 pestañas**:
  1. **Resumen:** clave `proyecto::coleccion`, base de datos, descripción y número de campos.
  2. **Diagrama:** diagrama ER filtrado automáticamente a esta colección y las colecciones vecinas con las que tiene relación directa.
  3. **Asociados** *(con 2 subpestañas)*: **Base de datos** (proyecto padre) y **Campos** (lista de Campos MongoDB de esta colección + botón `+ Añadir campo`).
  4. **Datos (Explorador de Documentos):** tabla en vivo que consulta los documentos reales guardados en MongoDB Atlas, con botón **Cargar más** (paginación keyset `after`), **Copiar JSON** y vista de detalle de cada documento (`dlgColDatosDetalle`).

### 3. Tabla de campos
| Campo (API / JSON) | Dónde se guarda | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `proyectos.colecciones[].id` | `string` (`/^[a-zA-Z_][a-zA-Z0-9_]*$/`) | Sí | Nombre físico de la colección en MongoDB (ej. `negocios`, `llamadas`). |
| `key` | *(calculado por la API)* | `string` (`llamadas::clientes`) | Auto | Identificador compuesto `proyectoId::coleccionId` usado en el catálogo del panel. |
| `proyectoId` | `proyectos.id` | `string` (`llamadas`) | Auto | ID de la Base de datos a la que pertenece. |
| `baseDatos` | `proyectos.base_datos` | `string` (`software_llamadas`) | Auto | Nombre de la base de datos en MongoDB. |
| `descripcion` | `proyectos.colecciones[].descripcion` | `string` | No | Qué tipo de documentos almacena esta colección. |
| `modo_escritura` | `proyectos.colecciones[].modo_escritura` | `"unico_por_negocio"` \| `"multiple"` | No | **Regla de identidad en MongoDB:** define si existe 1 solo documento por negocio (`1:1`) o muchos documentos por negocio (`1:N`). |
| `color` | `proyectos.colecciones[].color` | `string \| null` (`#RRGGBB`) | No | Color del icono en el panel. |
| `nCampos` | *(calculado contando `campos_mongo`)* | `number` | Auto | Cuántos Campos MongoDB están registrados en esta colección. |

### 4. Explicación a fondo de `modo_escritura`: `unico_por_negocio` (1:1) vs. `multiple` (1:N)

Esta es una de las piezas más importantes del **Motor Universal**:

| Modo de escritura | Qué colecciones lo usan | Cómo calcula el motor el `_id` del documento en MongoDB | Cómo se comporta cuando una Corrida escribe salidas |
|---|---|---|---|
| **`"unico_por_negocio"` (1:1)** | Por defecto las colecciones llamadas **`negocios`** y **`procesos`** (y cualquier otra donde pongas `"modo_escritura": "unico_por_negocio"`). | • En `negocios`: `_id = "<negocioId>"` (ej. `"pelo-sur"`).<br>• En `procesos`: `_id = "<negocioId>-proceso"` (ej. `"pelo-sur-proceso"`).<br>• En otra colección 1:1: `_id = "<negocioId>-<coleccion>"`. | Todas las corridas de `pelo-sur` leen y actualizan (`upsert`) **siempre la misma ficha única** del negocio. Nunca se duplican fichas de negocio. |
| **`"multiple"` (1:N)** | Por defecto **todas las demás colecciones** (`llamadas`, `reservas`, `clientes`, `versiones`, `reservas_prueba`, etc.). | 1) Si `corrida.datos._documentos_[coleccion]` ya tiene un `_id` activo, usa ese.<br>2) Si una salida trae el `_id` o un disparador lo fijó al arrancar, lo guarda en `_documentos_[coleccion]`.<br>3) Si es la primera escritura de la corrida en esa colección, crea un ID nuevo con formato **`<4letrasColeccion>-<corridaIdSinPrefijo>`** (ej. `llam-92a52d221c8349ee`) y lo anota en `corrida.datos._documentos_["llamadas"]`. | **Cada corrida nueva crea su propio documento histórico** (una llamada nueva, una reserva nueva), pero si una misma corrida tiene **varios pasos seguidos** que escriben en `llamadas`, todos los pasos de esa corrida actualizan **ese mismo documento** gracias a `corrida.datos._documentos_`. |

### 5. Conexiones (Hacia arriba y hacia abajo)
- **Hacia arriba:** Pertenece a una **Base de datos / Proyecto** (`proyectoId`).
- **Hacia abajo:**
  - Contiene los **Campos MongoDB** (`campoMongo.coleccion`) y los **Campos ancla** (`ancla.coleccion`).
  - Es vigilada por los **Disparadores** de tipo `cambio_datos` y `horario` (`disparador.coleccion`).
  - Sus cambios generan documentos en **Eventos** (`evento.coleccion`).

### 6. Reglas y límites que no se pueden romper (Invariantes)
- **Colecciones reservadas del sistema:** Las colecciones internas `corridas` y `eventos` están marcadas en `SYSTEM_COLLECTIONS`: escribir en ellas nunca dispara eventos `cambio_datos` para evitar recursión infinita.
- **Límites de seguridad del Explorador de Documentos (`GET .../documentos`):**
  - Exige siempre cabecera `Authorization: Bearer inv_...`.
  - Límite máximo por página: `limit <= 100` (por defecto `50`), timeout de consulta `8000 ms` y tamaño máximo de respuesta `1,5 MB`.
  - No permite `fields=*` ni operadores fuera de la lista segura (`$eq`, `$in`, `$gt`, `$gte`, `$lt`, `$lte`, `$ne`, `$exists`, `$regex` de hasta 200 caracteres).
  - Si un campo está vinculado a un Campo ancla con `sensible: true`, su valor se reemplaza automáticamente por `"[redactado]"` salvo que se pida explícitamente `?incluirSensible=1`.

### 7. Ejemplo real en producción
```json
{
  "key": "llamadas::llamadas",
  "id": "llamadas",
  "descripcion": "",
  "color": "#8a6a2a",
  "proyectoId": "llamadas",
  "proyectoNombre": "Software de llamadas",
  "baseDatos": "software_llamadas",
  "nCampos": 3
}
```

## Objeto 4 · Campo MongoDB (`campos_mongo`)

### 1. Qué es (en 1 frase)
Es la definición física de una columna o propiedad dentro de una colección de MongoDB, con su tipo de dato BSON (`string`, `date`, `bool`, `array`, `object`), su lista de valores permitidos (`enum`) y sus subcampos (`hijos[]`).

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:** Tabla `campos_mongo`.
- **En MongoDB Atlas:** Al empujar el esquema (`POST /v1/proyectos/:id/crear-bd`), cada fila de `campos_mongo` se compila dentro del validador nativo `$jsonSchema` de su colección en Atlas.
- **En la API (`/v1/mongo`):**
  - `GET /v1/mongo?proyecto=` y `GET /v1/mongo/:id` *(públicos)*.
  - `POST /v1/mongo`, `PUT /v1/mongo/:id` y `DELETE /v1/mongo/:id` *(requieren `Bearer inv_...`)*.
  - `POST /v1/helpers/proyeccion-array` *(requiere `Bearer inv_...`)*: utilidad para proyectar estructuras planas a arrays de MongoDB.
- **En el Panel UI:** Barra lateral **Catálogo → Campos** (`#panel-campos-mongodb`). Al abrir un campo (`dlgMongoFicha`) muestra **4 pestañas**:
  - **Definición:** colección, clave, tipo BSON, obligatorio, `enum`, `hijos[]` (si es `object` o `array`) y descripción.
  - **Asociados → Colección:** enlace directo para abrir la ficha de su Colección.
  - **Ancla:** muestra y abre el **Campo ancla** (`_..._`) con el que está emparejado.
  - **Interno:** `id`, `baseDatos`, `hash`.

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `id` | `string` (`llamadas-resultado`) | Sí | Identificador único del campo (normalmente `coleccion-clave`). |
| `campo` | `campo` | `string` (`llamadas.resultado`) | Sí | Ruta completa `coleccion.clave`. |
| `proyecto` | `proyecto` | `string` (`llamadas`) | Sí | ID de la Base de datos a la que pertenece. |
| `baseDatos` | `base_datos` | `string` (`software_llamadas`) | Sí | Nombre físico de la BD en MongoDB. |
| `coleccion` | `coleccion` | `string` (`llamadas`) | Sí | Nombre de la colección donde reside el campo. |
| `clave` | `clave` | `string` (`resultado` o `recorrido.pasos`) | Sí | Nombre de la propiedad dentro del documento JSON de MongoDB. |
| `bsonType` | `bson_type` | `string` (`string`, `number`, `int`, `long`, `double`, `decimal`, `bool`, `date`, `object`, `array`, `objectId`) | Sí | Tipo de dato físico que MongoDB Atlas validará en `$jsonSchema`. |
| `obligatorio` | `obligatorio` | `boolean` (`0` o `1` en D1) | No | Si es `true`, se incluye en el array `required: [...]` del `$jsonSchema` de la colección. |
| `enum` | `enum_json` | `string[]` (`["contesto", "no_contesto", "cita"]`) | No | Lista cerrada de valores permitidos para campos `string`. |
| `hijos` | `hijos` | `Array<{ id, clave, bsonType, obligatorio, descripcion }>` | Sí (si `object` o `array`) | Estructura interna de subcampos cuando `bsonType` es `object` o `array` de objetos (ej. `versiones.recorrido.pasos`). |
| `ancla` | `ancla` | `string` (`_llamada.resultado_`) | No | Nombre del **Campo ancla** emparejado con este campo físico. |
| `indices` | `indices` | `Array<{ nombre, campos, unico? }>` | No | Índices secundarios definidos sobre este campo. |
| `proyeccionMongo` / `proyeccionElemento` | `proyeccion_mongo` / `proyeccion_elemento` | `string` | No | Reglas opcionales de proyección para arrays anidados. |
| `color` | `color` | `string \| null` (`#RRGGBB`) | No | Color del icono en el catálogo. |

### 4. Conexiones (Hacia arriba y hacia abajo)
- **Hacia arriba:** Pertenece a una **Colección** (`coleccion`) dentro de una **Base de datos / Proyecto** (`proyecto`).
- **En paralelo (enlace 1:1):** Se sincroniza bidireccionalmente con un **Campo ancla** (`campoMongo.ancla ↔ ancla.ancla`).

### 5. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:**
  - Al crear o editar un Campo MongoDB, la API verifica que su `coleccion` exista en el proyecto y, si el cluster tiene `autoSync: true`, programa automáticamente el empuje del `$jsonSchema` a Atlas (`scheduleDebouncedSchemaSync`).
  - Si tiene un `ancla` asociada, mantiene sincronizados `baseDatos`, `coleccion` y `claveMongo` en la tabla `anclas`.
- **En Tiempo de Ejecución:**
  - Define qué campos están permitidos en los filtros, ordenaciones y proyecciones del **Explorador de Documentos** (`src/coleccion-documentos.ts`).
  - Sirve de mapa físico para que el motor sepa en qué ruta (`clave`) leer y escribir cada ancla en MongoDB.

### 6. Reglas y límites que no se pueden romper (Invariantes)
- **Colección válida obligatoria (`400 Bad Request`):** No se puede crear un Campo MongoDB en una colección que no esté previamente declarada dentro de `proyecto.colecciones`.
- **Subcampos en objetos y arrays:** Si `bsonType` es `"object"` o `"array"`, `hijos` debe ser un array válido.

### 7. Ejemplo real en producción (`llamadas-resultado` y `versiones-recorrido-pasos`)
```json
{
  "id": "llamadas-resultado",
  "campo": "llamadas.resultado",
  "proyecto": "llamadas",
  "baseDatos": "software_llamadas",
  "coleccion": "llamadas",
  "clave": "resultado",
  "bsonType": "string",
  "obligatorio": true,
  "enum": ["contesto", "no_contesto", "cita"],
  "descripcion": "Resultado de la llamada.",
  "ancla": "_llamada.resultado_",
  "hijos": [],
  "indices": []
}
```

## Objeto 5 · Campo ancla (`anclas`)

### 1. Qué es (en 1 frase)
Es el nombre canónico y universal de un dato, escrito siempre entre guiones bajos (`_ruta.del.campo_`), que actúa como contrato único entre las Skills, los Flujos y MongoDB.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `anclas`: definición canónica del ancla, su mapeo a MongoDB (`base_datos`, `coleccion`, `clave_mongo`), `aliases` y `sensible`.
  - Tabla `ancla_valores_negocio`: almacena el último valor conocido (`valor_actual`) y el historial de `observaciones` **por cada negocio** (`PRIMARY KEY (negocio_id, ancla_id)`).
  - Tabla `skill_anclas`: registra qué skills usan cada ancla como `'entrada'` o como `'salida'`.
- **En MongoDB Atlas:** Sus valores reales por cliente viven en el documento de `base_datos.coleccion` bajo la propiedad `clave_mongo`, y durante una corrida viajan dentro de `corrida.datos["_ruta.del.campo_"]`.
- **En la API (`/v1/anclas`):**
  - `GET /v1/anclas` y `GET /v1/anclas/:id?negocio_id=` *(públicos)*.
  - `GET /v1/anclas/resolve?q=<nombre_o_alias>` *(público)*: recibe cualquier nombre o alias (ej. `salon_name`) y devuelve el Campo ancla canónico (`_negocio.nombre_`).
  - `POST /v1/anclas`, `PUT /v1/anclas/:id` y `DELETE /v1/anclas/:id` *(requieren `Bearer inv_...`)*.
  - `GET /v1/anclas/:id/valores?negocio_id=` *(público)* y `POST /v1/anclas/:id/observaciones` *(requiere `Bearer inv_...`)*: leen y registran valores/observaciones de esa ancla para un negocio concreto.
- **En el Panel UI:** Barra lateral **Catálogo → Campos ancla** (`#panel-campos-ancla`). Al hacer clic en un ancla se abre `dlgCampoFicha` con **4 pestañas**:
  1. **Definición:** etiqueta, `ancla`, tipo, `obligatorio`, `sensible`, `formato`, `aliases[]`, descripción y ejemplo.
  2. **Historial:** observaciones registradas por negocio (`ancla_valores_negocio`).
  3. **Asociados** *(con 2 subpestañas)*: **Campo** (enlace al Campo MongoDB hermano) y **Skills** (lista de skills que la leen o escriben).
  4. **Interno:** `id`, `baseDatos`, `coleccion`, `claveMongo` y `hash`.

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `anclas.id` | `string` (`negocio.telefono`) | Sí | Identificador sin los guiones bajos de los extremos. |
| `ancla` | `anclas.ancla` | `string` (`_negocio.telefono_`) | Sí | Clave canónica con `_` al principio y al final (la API los añade sola si faltan). |
| `etiqueta` | `anclas.etiqueta` | `string` («Teléfono del negocio») | No | Nombre humano que se muestra en las listas del panel. |
| `baseDatos` | `anclas.base_datos` | `string` (`software_reservas`) | Sí | Base de datos de MongoDB donde vive este dato. |
| `coleccion` | `anclas.coleccion` | `string` (`negocios`) | Sí | Colección de MongoDB donde se lee y se guarda. |
| `claveMongo` | `anclas.clave_mongo` | `string` (`telefono`) | Sí | Ruta exacta dentro del documento de MongoDB (soporta rutas anidadas con puntos, como `recorrido.llega_a_b`). |
| `tipo` | `anclas.tipo` | `string` (`string`, `number`, `boolean`, `date`, `array`, `object`) | Sí | Tipo de dato del valor. |
| `obligatorio` | `anclas.obligatorio` | `boolean` | No | Indica si el campo es requerido en el esquema. |
| `sensible` | `anclas.sensible` | `boolean` | No | Si es `true` (o si `formato` incluye la palabra `sensible`), el Explorador de Documentos oculta su contenido mostrando `"[redactado]"`. |
| `formato` | `anclas.formato` | `string` | No | Formato o restricción adicional (ej. `enum:pendiente,confirmada,cancelada`). |
| `aliases` | `anclas.aliases` | `string[]` (`["salon_name", "nombre_local"]`) | No | Sinónimos que el motor reconoce automáticamente en webhooks y resoluciones. |
| `descripcion` | `anclas.descripcion` | `string` | No | Explicación funcional del dato. |
| `ejemplo` | `anclas.ejemplo` | `string` | No | Ejemplo real del valor esperado. |
| `skills` | *(tabla `skill_anclas`)* | `string[]` | Auto | IDs de las skills que tienen esta ancla en sus `entradas[]` o `salidas[]`. |

### 4. Anclas de catálogo vs. Anclas efímeras de sistema (`_consulta.*_` y `_redactor.*_`)
En Campos ancla existen dos clases de anclas:
1. **Anclas persistentes del catálogo (`anclas` en D1):** Mapean a una colección y clave física de MongoDB (como `_negocio.nombre_` o `_llamada.resultado_`). Cuando una skill las devuelve en `salidas`, el motor las escribe en MongoDB Atlas.
2. **Anclas efímeras de trabajo en memoria:** Usadas por las herramientas internas durante una corrida para pasarse parámetros de un nodo a otro dentro de `corrida.datos` sin necesidad de guardarlas en una tabla de negocio:
   - `_consulta.coleccion_` y `_consulta.pipeline_`: entradas de la skill interna `consultar-datos` (y `transformar-datos`).
   - `_consulta.resultado_` (array de documentos) y `_consulta.total_` (número): salidas que deja `consultar-datos` en `corrida.datos` para que el siguiente nodo (por ejemplo un `decision` o un `subflujo` con `sobre_ancla: "_consulta.resultado_"`) las utilice inmediatamente.

### 5. Conexiones (Hacia arriba y hacia abajo)
- **En paralelo (1:1):** Emparejado automáticamente con su **Campo MongoDB** (`campos_mongo`).
- **Hacia abajo:**
  - Es el lenguaje de **entradas y salidas** de todas las **Skills**.
  - Los **Disparadores** hidratan anclas automáticamente en `corrida.datos` al recibir un webhook o un cambio en MongoDB.
  - Los nodos **`decision`** evalúan condiciones sobre anclas y los nodos **`subflujo`** iteran sobre anclas de tipo array (`sobre_ancla`).

### 6. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:** Al crear un Campo ancla en un proyecto válido, la API crea o actualiza automáticamente su **Campo MongoDB** correspondiente para que el esquema físico y el catálogo de anclas nunca se desincronicen.
- **En Tiempo de Ejecución:**
  - **Lectura (`resolveEntradasValores`):** Antes de ejecutar una skill, el motor busca cada ancla de `entradas[]` primero en `corrida.datos` (valores recién calculados o hidratados por el disparador) y, si no está ahí, busca el documento en MongoDB (`findDocForCorrida`) y extrae `getByPath(doc, ancla.claveMongo)`.
  - **Escritura (`writeSalidasMongo`):** Al terminar una skill, por cada ancla devuelta en `salidas`, el motor localiza el documento destino según `modo_escritura` (`unico_por_negocio` o `multiple` vía `_documentos_`), escribe `setByPath(doc, ancla.claveMongo, valor)` en MongoDB y guarda una copia espejo en `ancla_valores_negocio`.

### 7. Reglas y límites que no se pueden romper (Invariantes)
- **Separación estricta entre catálogo y datos de cliente (`400 Bad Request`):** Está prohibido enviar `valorActual` u `observaciones` en `POST /v1/anclas` o `PUT /v1/anclas/:id`. Los valores de cada cliente se guardan por `negocio_id` mediante `POST /v1/anclas/:id/observaciones` o `/v1/ejecutar/:skill/salidas`.
- **Normalización automática de guiones bajos:** Cualquier referencia a un ancla (`negocio.url` o `_negocio.url_`) es normalizada por `normalizeAnclaToken` al formato `_negocio.url_`.

### 8. Ejemplo real en producción (`negocio.telefono`)
```json
{
  "id": "negocio.telefono",
  "ancla": "_negocio.telefono_",
  "etiqueta": "Teléfono del negocio",
  "claveMongo": "telefono",
  "coleccion": "negocios",
  "baseDatos": "software_reservas",
  "tipo": "string",
  "obligatorio": false,
  "formato": "",
  "descripcion": "Teléfono principal de contacto del negocio.",
  "ejemplo": "+34 928 000 000",
  "skills": ["descubrir-negocio"],
  "aliases": ["contacto.telefono", "telefono_local"],
  "sensible": false
}
```
