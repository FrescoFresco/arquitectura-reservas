## Mapa del Bloque D (Objetos 14 al 16)

El **Bloque D** agrupa las tres piezas que permiten **diseñar sin escribir JSON a mano**, **controlar quién tiene permiso de escritura en la API** y **documentar el conocimiento del sistema**:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 14. REDACTOR (POST /v1/redactor · Skill: `generar-definicion`)              │
│     Traduce una intención en español ──► JSON validado de:                  │
│     • un Flujo (`nodos[]` + `aristas[]`)                                    │
│     • un Disparador (`tipo`, `cron`, `coleccion`, `pipeline[]`)             │
│     • un Pipeline suelto (`$match`, `$lookup`, `$project`, ...)             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ 15. AGENTE E INVITE (D1: `agentes` + `invites` · Panel: Ajustes → Agentes)  │
│     Llaves de seguridad `Authorization: Bearer inv_...` para mutar el hub   │
│     (No confundir nunca con el Objeto #8 `Ejecutor`)                        │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ 16. FUNDAMENTO (D1: `fundamentos` + `fundamento_versions`)                  │
│     Documentos versionados en Markdown de la sección Documentación          │
└─────────────────────────────────────────────────────────────────────────────┘
```

## Objeto 14 · Redactor (`/v1/redactor`)

### 1. Qué es (en 1 frase)
Es el asistente de Tiempo de Diseño (integrado en el panel y en `POST /v1/redactor`) que recibe una frase en español («intención») y devuelve una definición JSON válida para un **Flujo**, un **Disparador** o un **Pipeline**, usando únicamente las colecciones, skills y anclas reales del catálogo.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1 / MongoDB:** No es una tabla estática; es un servicio respaldado por la skill interna `generar-definicion`. Cada vez que se invoca deja un registro de auditoría en D1 (`skill_ejecuciones`) y, si hay proyecto activo, en MongoDB (`ejecuciones`).
- **En la API (`/v1/redactor`):**
  - `GET /v1/redactor` *(público)*: devuelve el contrato de uso del Redactor y los esquemas soportados.
  - `POST /v1/redactor` *(requiere `Authorization: Bearer inv_...`; si no se envía Bearer responde `401 Unauthorized`)*: genera y valida la definición JSON.
- **En el Panel UI:** No es una pestaña suelta del menú lateral, sino un bloque empotrado directamente donde se editan las definiciones:
  1. En **Catálogo → Flujos → [abrir un Flujo] → pestaña Documento**: caja de texto de intención + botones **Generar** (`btnFlujoRedactorGenerar`), **Probar** (`btnFlujoRedactorProbar`) y **Guardar versión** (`btnGuardarFlujoVersion`).
  2. En **Catálogo → Flujos → [abrir un Flujo] → pestaña Disparadores → Añadir/Editar disparador (`dlgDisparador`)**: caja de intención + botones **Generar** (`btnDispRedactorGenerar`), **Probar** (`btnFlujoDispProbar`) y **Guardar** (`btnFlujoDispGuardar`).

### 3. Tabla de campos de Entrada y Salida (`POST /v1/redactor`)
| Dirección | Campo (JSON) | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| **Entrada** | `intencion` | `string` («cada hora, reservas sin confirmar de hace más de 2 horas») | Sí | Lo que quieres que haga el flujo, disparador o consulta, escrito en español normal. |
| **Entrada** | `tipo_definicion` | `"disparador"` \| `"flujo"` \| `"pipeline"` | Sí | Qué clase de estructura JSON debe construir el Redactor. |
| **Entrada** | `definicion_actual` | `object \| array \| null` | No | Si estás refinando un flujo o disparador ya existente, se le pasa el JSON actual para que lo modifique sin perder su `id`. |
| **Entrada** | `origen` | `string` (`"panel"`, `"api"`) | No | Etiqueta de auditoría para `skill_ejecuciones`. |
| **Salida** | `definicion` | `object \| array` | Auto | El JSON generado listo para previsualizar, probar o guardar. |
| **Salida** | `explicacion` | `string` (2–3 frases en español) | Auto | Resumen claro de qué hizo el Redactor o aviso si falta crear alguna skill en el catálogo. |
| **Salida** | `validacion` | `{ ok: boolean, errores: string[], avisos: string[] }` | Auto | Resultado del validador determinista del Worker (`validarDefinicion`). |
| **Salida** | `modo` / `modelo` | `"openai"` \| `"mock"` | Auto | Indica si se generó con el modelo configurado en el ejecutor de `generar-definicion` o con el motor heurístico `mock` (cuando no hay secret de proveedor en el Worker). |

### 4. El ciclo de 5 pasos del Redactor (Diseño seguro)
1. **Escribir la intención:** describes en texto qué quieres que ocurra.
2. **Generar (`POST /v1/redactor`):** el Worker carga como contexto la lista real de `anclas`, `skills` y `colecciones` de tu catálogo y llama a la skill `generar-definicion`.
3. **Validar (`validarDefinicion`):** antes de devolverte la respuesta, el código del Worker comprueba sin IA:
   - Si es `flujo`: que tenga nodos `inicio` y `fin`, que todas las aristas conecten nodos existentes y que las skills referenciadas existan en el catálogo.
   - Si es `disparador` o `pipeline`: que el cron tenga 5 campos válidos, que la colección exista y que el pipeline solo use las 8 etapas permitidas (`$match`, `$lookup`, `$project`, `$group`, `$sort`, `$limit`, `$unwind`, `$addFields`).
4. **Probar en seco (`Dry-run`):** al pulsar **Probar** (`POST .../disparadores/probar`), el pipeline se ejecuta contra los últimos 50 eventos o documentos reales de MongoDB y te muestra cuántos habría lanzado (`habria_lanzado`) y una muestra de hasta 20 documentos, **sin crear ninguna corrida real**.
5. **Confirmar y Guardar:** solo cuando tú pulsas **Guardar**, la definición se persiste en D1 creando una versión nueva.

### 5. Regla de oro del Redactor
- **La IA solo actúa al diseñar, nunca al ejecutar:** Una vez que guardas el JSON de un disparador o de un flujo, en producción el motor ejecuta ese JSON de forma 100 % determinista, instantánea y con coste `0`.

### 6. Ejemplo real en producción (`POST /v1/redactor`)
```json
{
  "ok": true,
  "definicion": {
    "tipo": "horario",
    "cron": "0 * * * *",
    "coleccion": "reservas",
    "pipeline": [
      { "$match": { "$or": [{ "estado": "sin_confirmar" }, { "estado": "pendiente" }] } },
      { "$limit": 100 }
    ],
    "anti_bucle": true,
    "agrupar_segundos": 0,
    "negocio": ""
  },
  "explicacion": "Disparador horario cada hora sobre «reservas» filtrando reservas pendientes o sin confirmar.",
  "validacion": {
    "ok": true,
    "errores": [],
    "avisos": []
  },
  "modo": "openai",
  "modelo": "gpt-4o-mini"
}
```

## Objeto 15 · Agente e Invite (`agentes` + `invites`)

### 1. Qué es (en 1 frase)
Es una credencial de acceso y operador del hub (identificado por un token `inv_...`) que autoriza a un navegador humano, a un flujo de n8n o a un asistente externo a realizar operaciones de escritura (`POST`, `PUT`, `DELETE`) y lecturas protegidas en la API de Campos ancla.

### 2. Diferencia crítica: `Agente` (Objeto #15) vs. `Ejecutor` (Objeto #8)
Una de las dudas más frecuentes al empezar es confundir **Agente** (en *Ajustes → Agentes*) con **Ejecutor** (en *Catálogo → Ejecutores*). Son dos piezas totalmente distintas:

| Característica | Objeto #15 · `Agente` (`Ajustes → Agentes`) | Objeto #8 · `Ejecutor` (`Catálogo → Ejecutores`) |
|---|---|---|
| **Qué es** | Una **llave de seguridad (`Bearer inv_...`)** para poder llamar a los endpoints de escritura de la API del hub. | La **configuración técnica de quién hace una Skill** dentro de un flujo (un modelo OpenAI, una función interna, un webhook de n8n o un humano). |
| **Dónde vive** | Tablas `agentes` e `invites` en D1. | Tabla `ejecutores` en D1. |
| **Dónde está en el Panel** | Arriba a la derecha en **Ajustes → Agentes** (botón **Dar acceso**). | En la barra lateral en **Catálogo → Ejecutores**. |
| **Cuándo interviene** | En **cualquier petición HTTP de escritura** (`POST`, `PUT`, `DELETE`) o en el Explorador de Documentos: el middleware de la API comprueba que la cabecera `Authorization: Bearer inv_...` sea una invite válida y no revocada. | Cuando una **Corrida** llega a un nodo `skill` y el motor mira `skill.ejecutorId` para saber cómo ejecutar ese paso. |

### 3. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `invites`: almacena las llaves generadas (`clave` con formato `inv_<40_hex>`, `creada`, `usada_por`, `revocada`).
  - Tabla `agentes`: almacena los operadores registrados con una invite (`id`, `nombre`, `foto`, `descripcion`, `invite_usada`, `last_seen`, `hash`, `proyectos`, `lee`, `escribe`, `color`).
- **En la API:**
  - `POST /v1/invites` *(abierto para el botón «Dar acceso» del Panel UI)*: genera y guarda una nueva llave `inv_...`.
  - `POST /v1/agentes/registro` *(autenticado pasando `clave: "inv_..."` en el body)*: da de alta o actualiza la ficha del agente asociado a esa llave.
  - `POST /v1/agentes/latido` *(autenticado con `clave: "inv_..."` en el body)*: actualiza `last_seen` (el panel envía un latido cada 120 s).
  - `GET /v1/agentes` *(público)*: lista todos los agentes registrados en el hub.
  - `PUT /v1/agentes/:id` y `DELETE /v1/agentes/:id` *(requieren `Bearer inv_...`)*.
- **En el Panel UI:** Pestaña superior **Ajustes → Agentes** (`#panel-agentes`):
  - Botón **Dar acceso** (`dlgDarAcceso`): crea al instante un token `inv_...` y te da las instrucciones listas para copiar.
  - Al hacer clic en un agente de la lista se abre `dlgAgenteFicha` con **2 pestañas**: **Resumen** (nombre, `id`, `lastSeen`, invite usada) y **ACL** (`proyectos`, `lee`, `escribe`).

### 4. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `agentes.id` | `string` (`agente-e2e-n8n`) | Sí | Identificador único del operador/agente. |
| `nombre` | `agentes.nombre` | `string` («Agente E2E n8n») | Sí | Nombre visible en Ajustes → Agentes. |
| `descripcion` | `agentes.descripcion` | `string` | No | Para qué se usa esta llave (ej. «Credencial de n8n para entregar salidas»). |
| `inviteUsada` | `agentes.invite_usada` / `invites.clave` | `string` (`inv_...`) | Sí | Token secreto que se envía en `Authorization: Bearer inv_...` (o en la cabecera alternativa `X-Agente-Clave: inv_...`). |
| `lastSeen` | `agentes.last_seen` | `string` (ISO timestamp) | Auto | Última vez que este agente se registró o envió un latido (`/v1/agentes/latido`). |
| `proyectos` | `agentes.proyectos` | `string[]` (`["reservas"]`) | No | Metadato de proyectos asignados al agente. |
| `lee` / `escribe` | `agentes.lee` / `escribe` | `string[]` (`["*"]`) | No | Metadatos descriptivos de permisos de lectura/escritura (por defecto `["*"]`; en la API actual cualquier invite activa no revocada tiene permiso completo de escritura en el hub). |
| `color` | `agentes.color` | `string \| null` (`#RRGGBB`) | No | Color del icono en la lista de agentes. |

### 5. Reglas de autenticación en toda la API de Campos ancla
1. **Lecturas públicas (`GET`, `HEAD`, `OPTIONS`):** Todas las rutas `GET /v1/...` son públicas (salvo el Explorador de Documentos reales de clientes `GET /v1/proyectos/:id/colecciones/:col/documentos`, que exige `Bearer inv_...` por privacidad de datos).
2. **Escrituras protegidas (`POST`, `PUT`, `DELETE`):** Todas las rutas que crean, modifican o borran objetos exigen `Authorization: Bearer inv_...` (salvo `POST /v1/invites` para generar una llave desde el panel, `POST /v1/agentes/registro` y `/latido` que llevan la `clave` en el body, y `POST /v1/disparar/:flujo/:token` que se autentica con el `:token` propio del webhook).
3. **Borrado y revocación:** Al borrar un agente con `DELETE /v1/agentes/:id`, su fila desaparece de `agentes` y su llave `inv_...` puede revocarse para impedir futuros accesos.

### 6. Ejemplo real en producción (`reservas-pagweb`)
```json
{
  "id": "reservas-pagweb",
  "nombre": "Reservas pagweb",
  "foto": "",
  "descripcion": "Operador para el circuito de reservas web",
  "inviteUsada": "inv_TU_TOKEN_DE_AGENTE",
  "lastSeen": "2026-10-21T10:01:18.668Z",
  "color": null,
  "proyectos": ["reservas"],
  "lee": ["_negocio.telefono_", "_negocio.nombre_", "_proceso.url_inicio_"],
  "escribe": ["_ejecucion.respuesta.estado_", "_ejecucion.ultima_url_"]
}
```

## Objeto 16 · Fundamento (`fundamentos` + `fundamento_versions`)

### 1. Qué es (en 1 frase)
Es cada uno de los documentos maestros versionados en Markdown (como los 6 documentos que estás leyendo ahora mismo) que conforman la biblioteca oficial de conocimiento y arquitectura dentro del propio software.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `fundamentos`: cabecera del documento (`id`, `nombre`, `descripcion`, `hash`, `color`, `created_at`, `updated_at`).
  - Tabla `fundamento_versions`: historial de versiones inmutables (`fundamento_id`, `numero`, `fecha`, `markdown`, `ruta`, `nombre_archivo`, `hash`), con borrado en cascada `ON DELETE CASCADE`.
- **En la API (`/v1/fundamentos`):**
  - `GET /v1/fundamentos` *(público)*: devuelve todos los fundamentos **ordenados alfabéticamente por `nombre` (`ORDER BY nombre`)**. Por eso los nombres empiezan por `01 ·`, `02 ·`... para garantizar el orden pedagógico de lectura.
  - `GET /v1/fundamentos/:id` *(público)*: devuelve la ficha y todas las versiones de un fundamento.
  - `POST /v1/fundamentos` *(requiere `Bearer inv_...`)*: crea un nuevo fundamento con su versión `v1`.
  - `PUT /v1/fundamentos/:id` *(requiere `Bearer inv_...`)*: añade una versión nueva (`v2`, `v3`...) sin pisar las anteriores (o actualiza solo `color` si únicamente se envía `{ "color": "#..." }`).
  - `DELETE /v1/fundamentos/:id` *(requiere `Bearer inv_...`)*: elimina el fundamento y todas sus versiones de D1.
- **En el Panel UI:** Pestaña superior **Documentación → Fundamentos** (`#panel-fundamentos`). Al abrir un documento se abre el lector `dlgFundamento` con selector de **Historial de versiones**, selector de color y **2 pestañas**: **Documento** (el markdown renderizado) e **Interno** (`id`, `version`, `hash`).

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `fundamentos.id` | `string` (`01-vision-y-recorrido`) | No (en POST se autogenera de `nombre` si se omite) | Identificador único del documento (`/^[a-z0-9][a-z0-9._-]{0,120}$/`). |
| `nombre` | `fundamentos.nombre` | `string` (máx. 120 chars) | Sí | Título visible en la lista (ej. `01 · Visión general y recorrido de un dato`). |
| `descripcion` | `fundamentos.descripcion` | `string` (máx. 280 chars) | No | Subtítulo descriptivo que aparece al pasar el ratón o editar. |
| `color` | `fundamentos.color` | `string \| null` (`#2563eb`) | No | Color hexadecimal del icono del libro en la lista. |
| `markdown` *(en POST/PUT)* | `fundamento_versions.markdown` | `string` | Sí | Contenido completo del documento en formato Markdown. |
| `versiones` | `fundamento_versions` | `Array<{ numero, fecha, markdown, ruta, nombreArchivo, hash }>` | Auto | Lista ordenada de todas las versiones publicadas del documento. |

### 4. Reglas importantes al editar Fundamentos
1. **Para publicar cambios permanentes para todo el equipo, usa siempre la API (`/v1/fundamentos`):** El botón *Editar* del navegador guarda borradores locales en `localStorage` de ese navegador (`· local`), mientras que `POST /v1/fundamentos` y `PUT /v1/fundamentos/:id` con `Bearer inv_...` escriben directamente en la base de datos D1 compartida por todos.
2. **Usa diagramas ASCII en bloques ```` ``` ```` y tablas Markdown:** El lector de Fundamentos del panel renderiza tablas, listas, citas y bloques de código con nitidez inmediata, sin depender de librerías externas.
