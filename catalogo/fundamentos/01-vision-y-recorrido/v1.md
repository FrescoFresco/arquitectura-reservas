## 1. Qué es «Campos ancla» y su regla de oro

**Campos ancla** es el sistema central (hub) que diseña, gobierna y ejecuta las operativas de cualquier software de negocio (como el *Software de reservas* o el *Software de llamadas*).

Todo el sistema se rige por una **regla de oro inquebrantable**:

> **El cerebro vive en Campos ancla; los modelos de IA y n8n son solo manos ejecutoras.**
> - **Campos ancla** guarda la estructura de las bases de datos, el vocabulario de campos permitidos (`_anclas_`), las instrucciones (`Skills`), el orden de los pasos (`Flujos`), cuándo arrancan (`Disparadores`) y el estado exacto de cada proceso en marcha (`Corridas`).
> - **Los modelos de IA (OpenAI, xAI, Anthropic), las funciones internas y n8n** nunca deciden qué paso va después de cuál ni escriben libremente en la base de datos: reciben únicamente las `_anclas_` de entrada que la Skill declara y devuelven únicamente las `_anclas_` de salida que la Skill exige.

## 2. Cómo funciona como plantilla multi-empresa

En lugar de duplicar flujos o prompts para cada cliente (peluquería, restaurante o clínica), Campos ancla funciona como una **plantilla única multi-empresa**:

1. **Un solo Flujo y un solo System Prompt / Skill** se escriben usando **huecos con nombre fijo** llamados **Campos ancla** (por ejemplo: `_negocio.nombre_`, `_negocio.telefono_`, `_proceso.url_inicio_`).
2. **La colección `negocios` en MongoDB** guarda un documento por cada empresa cliente (por ejemplo, `_id: "pelo-sur"`, `_id: "barberia-norte"`, `_id: "clinica-sol"`).
3. **Cuando arranca una Corrida**, se le indica para qué `negocio` corre (por ejemplo, `"negocio": "pelo-sur"`). El motor rellena automáticamente las anclas de entrada leyendo los datos de ese negocio en MongoDB y guarda las salidas en los documentos de ese negocio.

```
                      PLANTILLA ÚNICA (Tiempo de Diseño — D1)
          ┌─────────────────────────────────────────────────────────────┐
          │  Flujo: "reservas-descubrir-mapear"                         │
          │  Skill: "descubrir-negocio"                                 │
          │    Entradas pedidas: [ "_negocio.url_" ]                    │
          │    Salidas exigidas: [ "_negocio.nombre_",                  │
          │                        "_negocio.telefono_",                │
          │                        "_proceso.url_inicio_" ]             │
          └──────────────────────────────┬──────────────────────────────┘
                                         │
              En Tiempo de Ejecución se hidrata según `corrida.negocio`
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
┌───────────────────────┐    ┌───────────────────────┐    ┌───────────────────────┐
│ Negocio: "pelo-sur"   │    │ Negocio: "asador-mar" │    │ Negocio: "clinica-luz"│
│ (Mongo: negocios)     │    │ (Mongo: negocios)     │    │ (Mongo: negocios)     │
│ _id: "pelo-sur"       │    │ _id: "asador-mar"     │    │ _id: "clinica-luz"    │
│ nombre: "Pelo Sur"    │    │ nombre: "Asador Mar"  │    │ nombre: "Clínica Luz" │
└───────────────────────┘    └───────────────────────┘    └───────────────────────┘
```

## 3. Tiempo de Diseño (D1) vs. Tiempo de Ejecución (MongoDB Atlas)

Para no perderse nunca en el sistema, basta con distinguir **dónde viven las definiciones** y **dónde viven los datos en movimiento**:

| Dimensión | Tiempo de Diseño (El Plano) | Tiempo de Ejecución (La Realidad en Vivo) |
|---|---|---|
| **Qué guarda** | Los catálogos, esquemas, instrucciones versionadas, grafos de flujos, reglas de disparo y llaves de acceso. | Los documentos reales de los clientes (`negocios`, `llamadas`, `reservas`) y la actividad del motor (`eventos`, `corridas`, `ejecuciones`). |
| **En qué base de datos vive** | **Cloudflare D1** (base de datos SQLite del Worker `campos-ancla-db`). | **MongoDB Atlas** (conectado mediante la URI cifrada del `Cluster`). *Excepción:* D1 guarda un índice ligero `corridas_index` para gestionar bloqueos (`lease_hasta`) y filtros rápidos. |
| **Objetos que pertenecen a este plano** | `Cluster`, `Base de datos (Proyecto)`, `Colección` (definición), `Campo MongoDB`, `Campo ancla`, `System prompt`, `Skill`, `Ejecutor`, `Flujo`, `Disparador`, `Redactor`, `Agente`, `Fundamento`. | Documentos de cada `Colección`, `Evento`, `Corrida` y `Ejecución`. |
| **Cuándo cambia** | Cuando un humano o agente edita el catálogo en el Panel UI o usa el **Redactor** y pulsa **Guardar / Empujar esquema**. | Cada vez que entra un webhook, cambia un documento en MongoDB, salta el reloj de cada minuto o avanza un paso de la cola `PASOS`. |

## 4. Mapa de las 4 capas y los 16 objetos del sistema

Todo el software se compone exactamente de **16 objetos** organizados en **4 bloques**. Ninguna pieza existe fuera de este mapa:

```
=====================================================================================
 BLOQUE A · CAPA DE DATOS (Dónde se guarda la información y cómo se nombra)
=====================================================================================
 [1. Cluster] ──alberga──► [2. Base de datos (Proyecto)] ──contiene──► [3. Colección]
   (URI Atlas)               (relaciones[], empujes[])                 (modo 1:1 o 1:N)
                                                                              │
                                                                          define
                                                                              ▼
                           [5. Campo ancla] ◄───enlace 1:1───► [4. Campo MongoDB]
                           (_negocio.url_)                      (negocios.url, BSON)

=====================================================================================
 BLOQUE B · CAPA DE TRABAJO (Qué tarea se hace y quién la ejecuta)
=====================================================================================
 [6. System prompt] ──tono/rol (0..1)──► [7. Skill] ◄──quién la corre── [8. Ejecutor]
   (markdown vN)                        (entradas[] y                  (modelo, herramienta,
                                         salidas[] en                   integracion/n8n,
                                         anclas, vN)                    humano, agente_externo)

=====================================================================================
 BLOQUE C · CAPA DE AUTOMATIZACIÓN (Cuándo arranca, por dónde camina y qué deja)
=====================================================================================
 [11. Evento] ──evalúa──► [10. Disparador] ──arranca──► [9. Flujo] (nodos y aristas)
 (cambio_datos,            (manual, horario,                 │
  webhook, horario)         cambio_datos, webhook            │ instancia en vivo (pin vN)
                            + Pipeline MongoDB)              ▼
                                                       [12. Corrida] (cola PASOS + lease)
                                                             │
                                                             └──registra cada intento──► [13. Ejecución]

=====================================================================================
 BLOQUE D · HERRAMIENTAS DE DISEÑO, SEGURIDAD Y CONOCIMIENTO
=====================================================================================
 [14. Redactor]              [15. Agente e Invite]             [16. Fundamento]
 (Texto ──► JSON validado     (Llaves Bearer inv_...            (Documentación versionada
  para Flujo/Disparador)       en Ajustes → Agentes)             en Documentación → Fundamentos)
```

### Resumen rápido de los 16 objetos y dónde encontrarlos en el Panel UI

| # | Objeto | Qué es en una frase | Dónde está en el Panel UI |
|---|---|---|---|
| **1** | **Cluster** | Servidor de MongoDB Atlas con su URI cifrada donde residen las bases de datos. | `Catálogo → Clusters` |
| **2** | **Base de datos (Proyecto)** | Un software completo (ej. `reservas` o `llamadas`) que agrupa sus colecciones, relaciones, skills y flujos. | `Catálogo → Base de datos` |
| **3** | **Colección** | Una tabla de documentos en MongoDB con su modo de escritura (`unico_por_negocio` 1:1 o `multiple` 1:N) y explorador de datos. | `Catálogo → Colecciones` |
| **4** | **Campo MongoDB** | Una propiedad física dentro de una colección de MongoDB con su tipo BSON y reglas de validación `$jsonSchema`. | `Catálogo → Campos` |
| **5** | **Campo ancla** | El nombre fijo entre guiones bajos (`_ruta.campo_`) que une las skills y los flujos con el Campo MongoDB. | `Catálogo → Campos ancla` |
| **6** | **System prompt** | Instrucción base reutilizable (rol, tono y límites) que se antepone a una skill cuando la ejecuta un modelo de IA. | `Catálogo → System prompts` |
| **7** | **Skill** | Tarea aislada con instrucción en markdown que declara qué anclas recibe de entrada (`entradas[]`) y cuáles devuelve (`salidas[]`). | `Catálogo → Skills` |
| **8** | **Ejecutor** | Configuración técnica de quién realiza el trabajo de una skill (`modelo`, `herramienta`, `integracion`, `humano` o `agente_externo`). | `Catálogo → Ejecutores` |
| **9** | **Flujo** | Grafo versionado de nodos (`inicio`, `skill`, `decision`, `espera`, `subflujo`, `fin`) y aristas que define el orden de un proceso. | `Catálogo → Flujos` |
| **10** | **Disparador** | Regla asociada a un flujo que vigila eventos o el reloj, filtra con un Aggregation Pipeline y lanza corridas. | `Catálogo → Flujos → [Flujo] → Disparadores` |
| **11** | **Evento** | Foto inmutable en MongoDB (TTL 30 días) de algo que acaba de ocurrir (`cambio_datos`, `webhook` o `horario`). | `Catálogo → Flujos → [Flujo] → Corridas → Eventos` |
| **12** | **Corrida** | Ejecución concreta de un flujo para un negocio, con su estado actual, sus datos acumulados (`_documentos_`) y sus pasos. | `Catálogo → Flujos → [Flujo] → Corridas` |
| **13** | **Ejecución** | Registro de auditoría de cada intento individual de correr una skill con un ejecutor (entradas, salidas, duración, coste y error). | `Catálogo → Ejecutores` (o `Skills`) `→ Ejecuciones` |
| **14** | **Redactor** | Traductor asistido que convierte una intención en español en el JSON validado de un flujo, disparador o pipeline. | Dentro de `Flujo → Documento` y `Disparador` |
| **15** | **Agente e Invite** | Identidad con llave de seguridad (`Bearer inv_...`) autorizada para hacer escrituras (`POST`/`PUT`/`DELETE`) en la API del hub. | `Ajustes → Agentes` |
| **16** | **Fundamento** | Documento versionado en markdown que explica la arquitectura y reglas del propio sistema. | `Documentación → Fundamentos` |

## 5. El «Recorrido de la sangre»: traza real de principio a fin

Para ver cómo los objetos trabajan juntos en tiempo real, sigamos el viaje exacto de un dato real en el proyecto **`llamadas`** (`baseDatos: "software_llamadas"`) cuando termina una llamada telefónica de un cliente para el negocio **`pelo-sur`**.

### Diagrama cronológico del recorrido

```
[PASO 1 · Exterior / n8n]
  Llamada HTTP: POST /v1/disparar/llamadas-prueba-n8n/ash7k4yp...
  Body JSON:    { "negocio": "pelo-sur", "_cliente.nombre_": "Ana", "_cliente.telefono_": "+34600111222" }
        │
        ▼
[PASO 2 · Objeto #11: EVENTO (MongoDB: software_llamadas.eventos)]
  Se inserta el documento `ev-3a919e08824d` con:
  tipo: "webhook", origen: "webhook:disp-webhook-llamadas-n8n", body: { ... }
        │
        ▼
[PASO 3 · Objeto #10: DISPARADOR (D1: disparadores)]
  Se evalúa `disp-webhook-llamadas-n8n` (activo=true, anti_bucle=true, agrupar_segundos=0).
  1) Corre en MongoDB: aggregate([ { $match: { _id: "ev-3a919e08824d" } }, ...pipeline ])
  2) Hidrata anclas automáticamente desde el body:
     `_cliente.nombre_ = "Ana"`, `_cliente.telefono_ = "+34600111222"`
        │
        ▼
[PASO 4 · Objeto #12: CORRIDA + Cola PASOS (MongoDB `corridas` + D1 `corridas_index`)]
  Nace la corrida `c-92a52d221c8349ee`:
  - Fija `flujo_version: 1` del Objeto #9 FLUJO `llamadas-prueba-n8n`
  - Estado inicial: `en_curso`, `paso_actual: "paso-n8n"`
  - Encola en Cloudflare Queue `PASOS`: { corrida_id: "c-92a52d221c8349ee", nodo_id: "paso-n8n", intento: 0 }
        │
        ▼
[PASO 5 · Consumidor de Cola + Bloqueo Lease (D1: corridas_index.lease_hasta)]
  El consumidor saca el mensaje de la cola y adquiere un lease atómico en D1 por `timeout_s` (60 s).
  Lee el nodo `paso-n8n` del Flujo ──► apunta al Objeto #7 SKILL `procesar-llamada-n8n`.
        │
        ▼
[PASO 6 · Objeto #7: SKILL + Objeto #5: CAMPO ANCLA (Resolución de entradas)]
  La skill `procesar-llamada-n8n` pide `entradas: ["_cliente.nombre_", "_cliente.telefono_"]`.
  El motor las toma de `corrida.datos` (hidratadas en el Paso 3) o, si faltaran, las buscaría en
  MongoDB siguiendo el Objeto #4 CAMPO MONGODB (`software_llamadas.clientes.nombre` y `telefono`).
        │
        ▼
[PASO 7 · Objeto #8: EJECUTOR + Objeto #13: EJECUCIÓN]
  La skill tiene asignado `ejecutorId: "n8n-webhook-llamadas"` (`tipo: "integracion"`, `asincrono: true`).
  - El motor hace POST al webhook de n8n enviando `corrida_id`, `nodo_id`, `negocio`, `entradas` y `salidas_esperadas`.
  - Deja la corrida en estado `esperando_integracion` y crea un registro en `ejecuciones` (`intento: 0`).
        │
        ▼
[PASO 8 · Entrega de salidas, Identidad 1:N (`_documentos_`) y Cierre]
  Cuando n8n termina, llama a `POST /v1/ejecutar/procesar-llamada-n8n/salidas` (con `Bearer inv_TU_TOKEN_DE_AGENTE`):
  Body: { "corrida_id": "c-92a52d221c8349ee", "nodo_id": "paso-n8n", "negocio": "pelo-sur",
          "valores": { "_llamada.cliente_id_": "cli-01", "_llamada.fecha_": "2026-10-26T10:30:00Z", "_llamada.resultado_": "cita" } }
  1) Validación de contrato: verifica que las 3 anclas estén en `salidas[]` de `procesar-llamada-n8n`.
  2) Escritura 1:N en MongoDB: como la colección `llamadas` tiene `modo_escritura: "multiple"`, crea el
     documento `_id: "llam-92a52d221c8349ee"` en `software_llamadas.llamadas` y anota en la corrida:
     `corrida.datos._documentos_ = { "llamadas": "llam-92a52d221c8349ee" }`.
  3) Emisión de Evento con Anti-bucle: esa escritura en `llamadas` genera un nuevo Evento `cambio_datos`
     con `origen: "corrida:c-92a52d221c8349ee"`, que no provoca bucle infinito gracias a `anti_bucle: true`.
  4) Avance final: el motor encola el siguiente nodo (`fin`), libera el lease y marca la corrida como `completada`.
```

## 6. Orden de lectura de los 6 documentos de Fundamentos

Para dominar el software de principio a fin, lee los documentos en este orden numérico:

1. **`01 · Visión general y recorrido de un dato`** *(este documento)*: el modelo mental, la plantilla multi-empresa, las 4 capas y la traza completa de un dato.
2. **`02 · Capa de datos: Clusters, Bases de datos, Colecciones, Campos y Anclas`**: fichas completas de los Objetos 1 al 5, modos de escritura 1:1 vs. 1:N, relaciones, empujes de esquema y explorador de datos.
3. **`03 · Capa de trabajo: System prompts, Skills y Ejecutores`**: fichas completas de los Objetos 6 al 8, contratos de entrada/salida, las 3 skills internas del sistema y los 5 tipos de ejecutores.
4. **`04 · Capa de automatización: Flujos, Disparadores, Eventos, Corridas y Ejecuciones`**: fichas completas de los Objetos 9 al 13, los 6 tipos de nodos, los 14 operadores de decisión, esperas por reloj, subflujos en abanico (`sobre_ancla`), máquina de estados y control de fallos.
5. **`05 · Herramientas de diseño y seguridad: Redactor, Agentes y Fundamentos`**: fichas completas de los Objetos 14 al 16, uso del Redactor con dry-run y diferencia entre `Agente` (llave de API) y `Ejecutor`.
6. **`06 · Guía práctica: Conexión con n8n y recetas de producción`**: los 3 modos de conectar n8n, cómo crear un proyecto nuevo en 8 pasos y recetas listas para copiar.
