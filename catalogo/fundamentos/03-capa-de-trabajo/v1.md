## Mapa de la Capa de Trabajo (Objetos 6 al 8)

La **Capa de Trabajo** separa tres decisiones que nunca deben mezclarse:
1. **Con qué tono y reglas generales se trabaja** (`6. System prompt`).
2. **Qué tarea concreta se hace y qué anclas entran y salen** (`7. Skill`).
3. **Quién o qué tecnología ejecuta esa tarea** (`8. Ejecutor`).

```
┌─────────────────────────────────────────┐   ┌─────────────────────────────────────────┐
│ 6. SYSTEM PROMPT (D1: system_prompts)   │   │ 8. EJECUTOR (D1: ejecutores)            │
│    Rol, tono y límites reutilizables    │   │    Quién realiza la tarea:              │
│    1 System Prompt ──► muchas Skills    │   │    - modelo (OpenAI / xAI / Anthropic)  │
│    (Cada Skill tiene 0 o 1 Prompt)      │   │    - herramienta (código interno CF)    │
└────────────────────┬────────────────────┘   │    - integracion (Webhook HTTP / n8n)   │
                     │                        │    - humano (aprobación en el Panel)    │
                     │ se antepone al MD      │    - agente_externo (polling por turnos)│
                     ▼                        └────────────────────┬────────────────────┘
┌──────────────────────────────────────────────────────────────────┴────────────────────┐
│ 7. SKILL (D1: skills + skill_versions + skill_anclas)                                 │
│    Contrato estricto de trabajo:                                                      │
│    • Entradas (`entradas[]`): lista de `_anclas_` que el motor lee antes de empezar   │
│    • Instrucción (`markdown` vN): qué debe hacer exactamente en este paso             │
│    • Salidas (`salidas[]`): lista de `_anclas_` que el motor exige y guarda al final  │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

## Objeto 6 · System prompt (`system_prompts`)

### 1. Qué es (en 1 frase)
Es una instrucción base versionada en markdown (rol, tono, formato de respuesta y prohibiciones generales) que se antepone automáticamente al markdown de una o varias Skills cuando las ejecuta un modelo de IA.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `system_prompts`: metadatos (`id`, `nombre`, `descripcion`, `hash`, `color`, `created_at`, `updated_at`).
  - Tabla `system_prompt_versions`: historial de versiones del texto (`system_prompt_id`, `numero`, `fecha`, `markdown`, `ruta`, `nombre_archivo`, `hash`).
  - Tabla `system_prompt_skills`: vínculo entre el System prompt y las Skills que lo usan (`PRIMARY KEY (system_prompt_id, skill_id)`).
- **En MongoDB Atlas:** No se guarda en MongoDB; cuando un ejecutor corre un paso, el número de versión usado queda registrado como `prompt_version` dentro del paso de la Corrida y en la colección `ejecuciones`.
- **En la API (`/v1/system-prompts`):**
  - `GET /v1/system-prompts` y `GET /v1/system-prompts/:id` *(públicos)*.
  - `POST /v1/system-prompts`, `PUT /v1/system-prompts/:id` y `DELETE /v1/system-prompts/:id` *(requieren `Bearer inv_...`)*.
- **En el Panel UI:** Barra lateral **Catálogo → System prompts** (`#panel-system-prompts`). Al abrir una fila se muestra la ficha (`dlgSystemPrompt`) con botón de **Historial de versiones** (`v1`, `v2`...) y **3 pestañas**:
  1. **Documento:** contenido markdown renderizado de la versión abierta.
  2. **Asociados → subpestaña Skills:** lista de las skills que llevan puesto este System prompt y botón de edición (`btnEditarSystemPromptSkills`) para marcar o desmarcar skills.
  3. **Interno:** `id`, versión actual y `hash` SHA-256.

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `system_prompts.id` | `string` (`agente-base`) | Sí | Identificador único en formato slug. |
| `nombre` | `system_prompts.nombre` | `string` (máx. 120 chars) | Sí | Nombre visible en el catálogo (ej. «Agente base»). |
| `descripcion` | `system_prompts.descripcion` | `string` (máx. 280 chars) | No | Resumen corto de qué rol o reglas define. |
| `skills` | *(tabla `system_prompt_skills`)* | `string[]` (`["descubrir-negocio"]`) | No | Lista de IDs de las skills que utilizan este System prompt. |
| `versiones` | *(tabla `system_prompt_versions`)* | `Array<{ numero, fecha, markdown, ruta, nombreArchivo, hash }>` | Sí | Historial inmutable de todas las versiones del texto markdown. |
| `color` | `system_prompts.color` | `string \| null` (`#9a3ab4`) | No | Color del icono en el catálogo. |
| `hash` | `system_prompts.hash` | `string` | Auto | Hash SHA-256 de la última versión del markdown. |

### 4. Conexiones (Hacia arriba y hacia abajo)
- **Hacia arriba:** Es un objeto raíz de la Capa de Trabajo.
- **Hacia abajo:** Se conecta con **Skills** en relación **`1 : N` (un System prompt puede aplicarse a muchas Skills, pero cada Skill tiene como máximo `0` o `1` System prompt)**.

### 5. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:**
  - Editar su texto markdown crea una versión nueva (`v2`, `v3`...) sin borrar las anteriores.
  - Si asignas una skill a un System prompt y esa skill ya tenía otro System prompt distinto, la API la mueve automáticamente al nuevo System prompt (reemplazo atómico en `system_prompt_skills`).
- **En Tiempo de Ejecución:**
  - Cuando el motor interno ejecuta un paso con un ejecutor de tipo `modelo` (`src/motor-pasos.ts:841-857`), busca la última versión del System prompt asociado a la skill y construye el mensaje `system` uniendo `[systemPrompt.markdown, skill.markdown].join("\n\n")`.
  - Cuando un agente externo consulta `GET /v1/ejecutar/:skillId` o `GET /v1/corridas/:id/siguiente`, la API le entrega el texto exacto del System prompt junto con la versión (`prompt_version`) para que el modelo externo actúe bajo las mismas reglas.

### 6. Reglas y límites que no se pueden romper (Invariantes)
- **Máximo 1 System prompt por Skill:** Una skill nunca puede tener dos System prompts a la vez (`0..1`).
- **Actualización de vínculos sin inflar versión:** Si haces `PUT /v1/system-prompts/:id` enviando solo `{ "skills": [...] }` o `{ "color": "#..." }` sin cambiar el markdown, la API actualiza las asociaciones sin crear una versión nueva en `system_prompt_versions`.

### 7. Ejemplo real en producción (`agente-base`)
```json
{
  "id": "agente-base",
  "nombre": "Agente base",
  "descripcion": "Tono y límites del agente",
  "color": "#9a3ab4",
  "skills": ["descubrir-negocio"],
  "versiones": [
    {
      "numero": 1,
      "fecha": "2026-10-20",
      "markdown": "# Agente base\n\nActúa con precisión, sin inventar selectores ni URLs. Devuelve siempre los campos ancla solicitados.",
      "ruta": "catalogo/system-prompts/agente-base/v1.md",
      "nombreArchivo": "agente-base.md",
      "hash": "3703456b74a71fc54529e35c0843c546d4baa89101150c10ad56aaa6ad14404c"
    }
  ]
}
```

## Objeto 7 · Skill (`skills`)

### 1. Qué es (en 1 frase)
Es una unidad de trabajo atómica y versionada que define **qué hay que hacer** (en markdown), **qué Campos ancla necesita recibir para empezar** (`entradas[]`), **qué Campos ancla está obligada a devolver al terminar** (`salidas[]`) y **qué Ejecutor la realiza** (`ejecutorId`).

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:**
  - Tabla `skills`: ficha principal (`id`, `nombre`, `descripcion`, `hash`, `color`, `ejecutor_id`, `created_at`, `updated_at`).
  - Tabla `skill_versions`: historial de versiones del markdown (`skill_id`, `numero`, `fecha`, `markdown`, `ruta`, `nombre_archivo`, `hash`).
  - Tabla `skill_anclas`: contrato estricto de entradas y salidas (`skill_id`, `ancla`, `direccion` con `CHECK (direccion IN ('entrada', 'salida'))`).
  - Tabla `ancla_skills`: unión total de anclas vinculadas a la skill.
  - Tabla `proyecto_skills`: con qué Bases de datos (Proyectos) está asociada.
  - Tabla `system_prompt_skills`: qué System prompt (`0..1`) lleva asignado.
- **En MongoDB Atlas:** Sus ejecuciones se auditan en la colección `ejecuciones` (y en D1 `skill_ejecuciones` para `generar-definicion`).
- **En la API (`/v1/skills` y `/v1/ejecutar/:skillId`):**
  - `GET /v1/skills` y `GET /v1/skills/:id` *(públicos)*.
  - `POST /v1/skills`, `PUT /v1/skills/:id` y `DELETE /v1/skills/:id` *(requieren `Bearer inv_...`)*.
  - `GET /v1/ejecutar/:skillId` *(público)*: devuelve el contrato completo listo para ejecutar (`entradas[]`, `salidas[]`, `systemPrompts[]`, `ejecutorId` y la última versión del `markdown`).
  - `GET /v1/ejecutar/:skillId/entradas?negocio=<id>` *(público)*: lee de MongoDB (con respaldo en D1) los valores actuales de las `entradas[]` de esta skill para ese negocio.
  - `POST /v1/ejecutar/:skillId/salidas` *(requiere `Bearer inv_...`)*: recibe `{ negocio, valores, corrida_id?, nodo_id? }`, valida que todas las claves de `valores` pertenezcan a `salidas[]`, las escribe en MongoDB y, si forma parte de una corrida, avanza la corrida al siguiente nodo.
  - `GET /v1/skills/:id/ejecuciones?limit=&proyecto=` *(público)*: historial de ejecuciones de esta skill.
- **En el Panel UI:** Barra lateral **Catálogo → Skills** (`#panel-skills`). Al hacer clic en una skill se abre `dlgSkill` con **6 pestañas principales**:
  1. **Documento:** instrucciones en markdown de la versión seleccionada.
  2. **Diagrama:** esquema visual de sus anclas de entrada → skill → anclas de salida.
  3. **Asociados** *(con 4 subpestañas)*:
     - **Anclas** *(con subpestañas **Entradas** y **Salidas**)*: permite editar la lista exacta de anclas que entran y salen.
     - **System prompt:** muestra y cambia el System prompt (`0..1`) asignado.
     - **Ejecutor:** muestra y cambia el Ejecutor (`ejecutorId`) asignado.
     - **Bases de datos:** proyectos donde participa esta skill.
  4. **Conexión:** muestra las rutas HTTP exactas (`/v1/ejecutar/:skillId/entradas` y `/salidas`) listas para copiar.
  5. **Ejecuciones:** tabla de auditoría con cada vez que se ha ejecutado la skill.
  6. **Interno:** `id`, versión y `hash`.

### 3. Tabla de campos
| Campo (API / JSON) | Columna / Tabla en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `skills.id` | `string` (`descubrir-negocio`) | Sí | Identificador único de la skill. |
| `nombre` | `skills.nombre` | `string` | Sí | Nombre descriptivo (ej. «Descubrir negocio»). |
| `descripcion` | `skills.descripcion` | `string` | No | Resumen de qué resuelve esta tarea. |
| `entradas` | `skill_anclas` (`direccion='entrada'`) | `string[]` (`["_negocio.url_"]`) | No | Lista de Campos ancla que el motor lee y entrega al ejecutor antes de correr la skill. |
| `salidas` | `skill_anclas` (`direccion='salida'`) | `string[]` (`["_negocio.nombre_", ...]`) | No | Lista de Campos ancla que el ejecutor debe devolver al terminar y que el motor guardará en MongoDB. |
| `anclas` | `ancla_skills` | `string[]` | Auto | Unión ordenada de `entradas` + `salidas`. |
| `ejecutorId` | `skills.ejecutor_id` | `string \| null` (`modelo-por-defecto`) | No | ID del **Ejecutor** que corre esta skill. Si es `null`, el motor asume implícitamente `agente_externo`. |
| `systemPrompts` | `system_prompt_skills` | `Array<{ id, nombre, descripcion, hash }>` (`0..1`) | No | System prompt asociado (como máximo 1 elemento). Al guardar en `POST`/`PUT` puedes pasar `systemPromptId`. |
| `versiones` | `skill_versions` | `Array<{ numero, fecha, markdown, hash }>` | Sí | Historial de versiones del documento markdown de la skill. |
| `color` | `skills.color` | `string \| null` (`#RRGGBB`) | No | Color del icono en el catálogo. |

### 4. Las 3 Skills internas del sistema (incluidas de serie en el Hub)
Además de las skills propias de cada negocio (`descubrir-negocio`, `mapear-recorrido`, `procesar-llamada-n8n`, etc.), Campos ancla incluye **3 skills universales** para operar datos y diseñar sin coste o con validación estricta:

| Skill interna (`id`) | Ejecutor asignado | Entradas (`entradas[]`) | Salidas (`salidas[]`) | Qué hace exactamente |
|---|---|---|---|---|
| **`consultar-datos`** | `herramienta-consultar-datos` (`tipo: "herramienta"`, `coste: 0`, sin IA) | `_consulta.coleccion_`, `_consulta.pipeline_` | `_consulta.resultado_`, `_consulta.total_` | Ejecuta en MongoDB un Aggregation Pipeline de solo lectura (solo etapas `$match`, `$lookup`, `$project`, `$group`, `$sort`, `$limit`, `$unwind`, `$addFields`; añade `$limit: 100` si no lleva `$limit`) y deja los documentos encontrados en `corrida.datos["_consulta.resultado_"]`. |
| **`transformar-datos`** | `herramienta-transformar-datos` (`tipo: "herramienta"`, `coste: 0`, sin IA) | `_consulta.pipeline_` | *(Dinámicas: cualquier clave `_ancla_` producida)* | Aplica etapas `$addFields` y/o `$project` directamente **en memoria** sobre `corrida.datos` sin llamar a ningún modelo ni a MongoDB. Cualquier campo con formato `_ancla_` calculado por `$addFields`/`$project` se vuelca en `corrida.datos` y, si existe en el catálogo de anclas, se guarda en MongoDB. |
| **`generar-definicion`** | `modelo-por-defecto` (`tipo: "modelo"`) | `_redactor.intencion_`, `_redactor.tipo_definicion_`, `_redactor.contexto_`, `_redactor.esquema_`, `_redactor.definicion_actual_` | `_redactor.definicion_`, `_redactor.explicacion_` | Es la skill que impulsa al **Redactor** (`POST /v1/redactor`) en tiempo de diseño para convertir texto en español en el JSON de un flujo, disparador o pipeline. |

### 5. Conexiones (Hacia arriba y hacia abajo)
- **Usa (hacia arriba / lateral):**
  - **Campos ancla** en `entradas[]` y `salidas[]`.
  - Un **System prompt** (`0..1`) para fijar su marco general.
  - Un **Ejecutor** (`ejecutorId`) que define quién hace el trabajo.
- **La usan (hacia abajo):**
  - Las **Bases de datos / Proyectos** (`proyecto_skills`) para componer el mapa de **Operativa**.
  - Los **Flujos** dentro de sus nodos de tipo `"skill"` (`nodo.skill → skill.id`).
  - Las **Corridas** y **Ejecuciones** en tiempo de ejecución.

### 6. Cómo actúa: Tiempo de Diseño vs. Tiempo de Ejecución
- **En Tiempo de Diseño:**
  - Cuando asocias skills a un proyecto, la pestaña **Operativa** del proyecto cruza automáticamente las `salidas[]` de unas skills con las `entradas[]` de otras para mostrarte el grafo de dependencias y avisarte si alguna `entrada` no la produce nadie (`⛔ hueco`).
- **En Tiempo de Ejecución:**
  1. Antes de ejecutar la skill, el motor resuelve sus `entradas[]` leyendo de `corrida.datos` y de MongoDB.
  2. El ejecutor realiza el trabajo y devuelve un objeto JSON con las `salidas`.
  3. El motor comprueba que **no falte ninguna salida declarada** (`Salidas faltantes: ...`) y que **no se intente colar ninguna ancla ajena a `salidas[]`**.
  4. Escribe los valores en MongoDB Atlas y los copia en `corrida.datos` para los siguientes nodos del flujo.

### 7. Reglas y límites que no se pueden romper (Invariantes)
- **Bloqueo estricto de salidas no declaradas (`400 Bad Request`):** Si alguien llama a `POST /v1/ejecutar/:skillId/salidas` enviando en `valores` un ancla que **no está declarada en `salidas[]` de esa skill**, la API rechaza toda la escritura con HTTP `400`.
- **Verificación de salidas completas en el motor interno:** Cuando el motor interno ejecuta un paso (`modelo`, `herramienta` o `integracion` síncrona), comprueba `salidasDecl.filter(a => !(a in salidas))`. Si falta alguna ancla prometida en `salidas[]`, marca error de validación (`Salidas faltantes: ...`) y reintenta como máximo 1 vez.
- **Comportamiento si se borra su Ejecutor:** La clave foránea `skills.ejecutor_id` tiene `ON DELETE SET NULL`. Si borras un ejecutor, la skill no se borra: su `ejecutorId` pasa a `null` (que equivale a `agente_externo`).

### 8. Ejemplo real en producción (`procesar-llamada-n8n`)
```json
{
  "id": "procesar-llamada-n8n",
  "nombre": "Procesar llamada n8n",
  "descripcion": "Envía los datos del cliente a n8n para registrar el resultado de la llamada.",
  "ejecutorId": "n8n-webhook-llamadas",
  "systemPrompts": [],
  "entradas": ["_cliente.nombre_", "_cliente.telefono_"],
  "salidas": ["_llamada.cliente_id_", "_llamada.fecha_", "_llamada.resultado_"],
  "anclas": ["_cliente.nombre_", "_cliente.telefono_", "_llamada.cliente_id_", "_llamada.fecha_", "_llamada.resultado_"]
}
```

## Objeto 8 · Ejecutor (`ejecutores`)

### 1. Qué es (en 1 frase)
Es la ficha técnica que configura **quién realiza el trabajo de una Skill** (un modelo de IA, una herramienta interna de código, un webhook HTTP como n8n, una persona desde el panel o un agente externo por turnos) junto con su tiempo máximo de espera (`timeout_s`) y su política de reintentos.

### 2. Dónde vive (Base de datos, API y Pantalla del Panel)
- **En Cloudflare D1:** Tabla `ejecutores` (`id`, `nombre`, `tipo`, `config_json`, `timeout_s`, `reintentos`, `espera_reintento_s`, `activo`, `version`, `color`, `created_at`, `updated_at`).
- **En MongoDB Atlas:** Cada vez que un ejecutor interviene en un paso, deja su huella en la colección `ejecuciones` (`ejecutor_id`, `ejecutor_version`).
- **En la API (`/v1/ejecutores`):**
  - `GET /v1/ejecutores` y `GET /v1/ejecutores/:id` *(públicos)*.
  - `POST /v1/ejecutores`, `PUT /v1/ejecutores/:id` y `DELETE /v1/ejecutores/:id` *(requieren `Bearer inv_...`)*.
  - `GET /v1/ejecutores/:id/ejecuciones?limit=&proyecto=` *(público)*: devuelve las últimas ejecuciones registradas en MongoDB para este ejecutor.
  - `GET /v1/integraciones/n8n/workflows` *(público)*: si el Worker tiene configurados los secrets `N8N_BASE_URL` y `N8N_API_KEY`, consulta la API de n8n y devuelve la lista de workflows disponibles (`id`, `nombre`, `activo`, `editor_url`, `webhook_url`) para autocompletar ejecutores de tipo `integracion`.
- **En el Panel UI:** Barra lateral **Catálogo → Ejecutores** (`#panel-ejecutores`). Al abrir un ejecutor (`dlgEjecutor`) tiene **4 pestañas**:
  1. **Resumen:** tipo, configuración detallada (`config`), `timeout_s`, `reintentos`, `espera_reintento_s`, estado `activo` y —si es una integración de n8n con `editor_url`— el botón directo **Abrir workflow en n8n ↗**.
  2. **Skills:** lista de las skills que tienen asignado este ejecutor.
  3. **Ejecuciones:** historial en vivo de llamadas a este ejecutor con su duración, coste, estado (`ok` / `error` / `esperando_integracion`) y detalle de entradas/salidas.
  4. **Interno:** `id`, `version`, fechas y color.

### 3. Tabla de campos
| Campo (API / JSON) | Columna en D1 | Tipo y valores permitidos | Oblig. | Qué significa en lenguaje llano |
|---|---|---|---|---|
| `id` | `id` | `string` (`modelo-por-defecto`) | Sí | Identificador único en formato slug (`/^[a-z0-9][a-z0-9-]{0,60}$/`). |
| `nombre` | `nombre` | `string` | Sí | Nombre legible del ejecutor. |
| `tipo` | `tipo` | `"modelo"` \| `"herramienta"` \| `"integracion"` \| `"humano"` \| `"agente_externo"` | Sí | Define cuál de los 5 mecanismos de ejecución utilizará el motor. |
| `config` | `config_json` | `object` *(ver tabla de los 5 tipos abajo)* | Sí | Parámetros específicos según el `tipo` de ejecutor. |
| `timeout_s` | `timeout_s` | `integer` (`1..3600`, por defecto `60`) | No | Segundos máximos que puede tardar un intento antes de abortarse o marcarse `timeout`. |
| `reintentos` | `reintentos` | `integer` (`0..20`, por defecto `2`) | No | Cuántas veces adicionales se reintentará el paso si falla. |
| `espera_reintento_s` | `espera_reintento_s` | `integer` (`0..3600`, por defecto `10`) | No | Segundos base para el backoff exponencial entre reintentos (`espera_reintento_s × 2^intento`). |
| `activo` | `activo` | `boolean` (`1` o `0` en D1, por defecto `true`) | No | Si se pone en `false`, el motor no lo invoca y cae al ejecutor implícito `agente_externo`. |
| `version` | `version` | `integer` (empieza en `1`) | Auto | Sube en `+1` cada vez que se edita el ejecutor con `PUT /v1/ejecutores/:id`. |
| `skills` | *(join con `skills.ejecutor_id`)* | `string[]` | Auto | IDs de las skills que usan actualmente este ejecutor. |
| `color` | `color` | `string \| null` (`#RRGGBB`) | No | Color del icono en el catálogo. |

### 4. Tabla comparativa de los 5 tipos de Ejecutor y su `config` exacta (`src/ejecutores.ts`)

| Tipo (`tipo`) | Qué campos exige o acepta `config` | Cómo lo ejecuta el motor cuando una Corrida llega a la Skill | Estado de la Corrida mientras corre |
|---|---|---|---|
| **`1. modelo`** | • `proveedor` (**obligatorio**): `"openai"` \| `"xai"` \| `"anthropic"`<br>• `modelo` (**obligatorio**): ej. `"gpt-4o-mini"`, `"grok-4"`<br>• `secret` (**obligatorio**): nombre del Secret en el Worker (ej. `"OPENAI_API_KEY"`)<br>• `temperatura` *(opcional)*: `0..2` (default `0`)<br>• `salida_json` *(opcional)*: `boolean` (default `true`) | El propio Worker llama por HTTP a la API del LLM enviando `systemPrompt + skill.markdown` y las `entradas`. ### 5. Política de Timeouts y Reintentos Exponenciales (`src/motor-pasos.ts`)
Cuando un intento de ejecución falla (o vence su `timeout_s`), el motor aplica estas reglas exactas (`shouldRetryPaso` y `retryDelaySeconds`):
1. **Errores que NUNCA se reintentan (`http4xx`):** Si una `integracion` responde HTTP `400..499` (por ejemplo `401 Unauthorized` o `404 Not Found`), el motor no gasta reintentos: marca el paso en `error` y la corrida pasa inmediatamente a `fallida`.
2. **Errores de validación de salidas (`validation`):** Si el modelo o integración devuelve un JSON incompleto (`Salidas faltantes: ...` o `no es JSON`), se permite como máximo **1 reintento** (`intento < 1`).
3. **Errores de red, HTTP 5xx o Timeouts (`retryable` / `timeout`):** Mientras `intento < reintentos`, el motor vuelve a encolar el paso en la cola `PASOS` con un retraso exponencial (`delaySeconds`):
   $$\text{delaySeconds} = \min\left(43200,\ \text{espera\_reintento\_s} \times 2^{\text{intento}}\right)$$
   - Ejemplo con `espera_reintento_s: 10` y `reintentos: 2`:
     - Fallo en `intento: 0` → espera $10 \times 2^0 = 10\text{ s}$ y lanza `intento: 1`.
     - Fallo en `intento: 1` → espera $10 \times 2^1 = 20\text{ s}$ y lanza `intento: 2`.
     - Fallo en `intento: 2` → agota reintentos y la corrida queda en estado **`fallida`** (lista para pulsar **Reintentar** manualmente desde el Panel).
